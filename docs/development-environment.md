# スキル開発環境の規約

共通の開発環境から、スキルとリポジトリツールを再現可能に検証する。
構造と保守方法は [共通仕様](skill-repository-spec.md) に従う。

## 環境を用意する

Git と Python 3.12 を基準環境とする。
ただし、別の Python バージョンを使う場合も、基準環境で検証できる状態を維持する。
コマンドはリポジトリのルートから実行する。

開発依存は `requirements-dev.txt` で管理し、プロジェクト内の `.venv` へ導入する。
POSIX 互換シェルでの手順を示す。

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements-dev.txt
python3 --version
python3 -m pytest --version
```

なお、別のシェルでは、そのシェルの方法で `.venv` を有効化する。
検証に必要な依存は開発依存へ記録し、システムの Python 環境を変更しない。
特定の端末の絶対パスや、手動設定した `PYTHONPATH` に依存させない。
また、仮想環境と再生成可能な検証出力は Git の追跡対象から除く。

## テストを保守する

スキル固有の自動テストは `skills/{{skill-name}}/tests/`、リポジトリツールのテストはルートの `tests/` に置く。
共通ランナーは pytest とし、収集設定はルートの `pytest.ini` に集約する。
配布物の `dist/` は収集対象から除き、テストも配布物へ含めない。

新規・変更するスキルのテストは、`test_*.py` の `test_*` 関数として収集できるようにする。
その際、外部から観測できる結果と重要な失敗条件を検証する。
ファイル操作は `tmp_path` などで隔離し、実行順序、外部ネットワーク、秘密情報、開発者の端末状態に依存させない。
共通 fixture が必要なら、最も狭い共有範囲の `conftest.py` に置く。

一方、文章による指示の品質は、現実的な依頼に対する振る舞いで確認する。
文章の文字数や特定の見出しの存在を、判断の正しさの代わりに検査しない。
そのため、決定的な処理がないスキルでは `tests/` を作らず、リポジトリ検査と前向き評価を行う。

## 完了ゲートを実行する

pytest は有効化した開発環境から `python3 -m pytest` で実行する。
変更したスキルをリポジトリ検査へ指定し、テストがあるスキルはそのディレクトリも指定する。

```bash
python3 scripts/validate_skills.py {{skill-name}}
python3 -m pytest skills/{{skill-name}}/tests
```

複数スキルのテストは、一回の実行へ対象ディレクトリを並べる。
ルートのツールだけを検証する場合は `python3 -m pytest tests` を使う。
一方、共通仕様、雛形、検査処理、開発依存など、全体に影響する変更では全スキルと全テストを検証する。

```bash
python3 scripts/validate_skills.py
python3 -m pytest tests skills
```

テストが存在しないディレクトリは指定しない。
テストの収集失敗や未実行を成功として扱わず、失敗は原因を直して再検証する。
検査を通すために必要なテストを削除したり、理由なく skip したりしない。

## 合成シナリオを前向き評価する

スキルの追加・削除や適用条件、実行時規則、合成規則を変えた場合は、`skill-composition.json` で影響するシナリオを評価する。
その際、単独シナリオの `skill` または組み合わせシナリオの `skills` だけを一時的な導入先へインストールし、新しいセッションへ `request` と作業に必要な素材を渡す。評価対象外のスキルや作業履歴が混入しない環境を使う。
ただし、期待する答え、`applicable_skills`、既知の問題、編集担当の検討履歴は渡さない。スキルの適用も、評価するエージェントが依頼と配布物から判断する。

Codex CLI を使う評価用サンプルは、`codex --version` で確認したインストール済みの版に合わせて用意する。その CLI を直接実行し、同じ版のソース根拠と実測を照合する。

実際の出力と成果物を、実行後に `expected` と `forbidden` へ照合する。組み合わせシナリオでは、適用した作業を `applicable_skills` とも照合し、導入されているだけのスキルが作業を増やしていないかを確認する。
その際、必要な要求の欠落と、根拠のない制約や作業の追加を、それぞれ確認する。
ただし、原則から妥当に判断できる結果は、想定した文面や構成と違っていても認める。
不適合があれば原因に応じて仕様、配布物、シナリオを直し、再評価する。

最終報告にシナリオ ID と結果を記載する。
なお、実行環境の不足で評価できないシナリオは、理由を添えて未評価とする。
モデル、日時、生成出力を台帳へ履歴として保存しない。
