# 人間の意図を、読み手が判断できる仕様として保つ

## 1. 問題意識――精密であることが、理解できることにつながっていない

仕様書に求めるのは、想定できる解釈をすべて封じることではない。人間が何を実現したいのか、何を大切にしているのか、どのような原則に従って判断すればよいのかが伝わることである。読み手は、その考え方を理解することによって、個々の場面で適切な判断ができる。重要な判断は明確に定まっているが、目的を満たす複数の実現方法があるところには、その選択の余地が残っている。そのような仕様書を望んでいる。

これに対して、問題にしているのは、主張の後へ「ただし、〇〇は含まない」という限定を重ねたり、同じ扱いをする対象を「A、B、C、……、X、Y、Z」と列挙したりすることで、局所的な精密さを積み上げていく文章である。個々の文を取り出せば、それぞれに説明の理由がある。しかし、全体を理解するためには、読み手が多数の条件を照合し、対象に入るものと入らないものを分類し、その背後にある意図を自分で復元しなければならない。

この負担は、単に文章が長いことから生じるのではない。本来は対象の役割や判断基準を伝えればよいところで、目的にとって重要でない区別まで仕様へ持ち込んでいることから生じる。列挙を箇条書きへ移しても、長い文を短く分けても、読み手が統合しなければならない条件の総体は変わらない。「ただし」という語を減らしても、同じ境界条件を別の言い方で残しているなら、問題は残っている。

もう一つの問題は、仕様書が現在の設計ではなく、過去の修正の経緯を保存する文章になってしまうことである。新しい要求が生じるたびに、既存の説明へ補足を加え、衝突する部分へ例外を設け、その例外によって生じる疑問へさらに注記を加える。そうしてできた文書には、個々の修正の正しさは残っていても、全体として何を実現する仕様なのかが見えにくい。

この二つは、独立した日本語表現上の問題と編集上の問題ではない。既存の文章を保存しようとする姿勢と、解釈の可能性をすべて明文化しようとする姿勢が重なることで、追記するほど精密になり、精密になるほど理解しにくい仕様書が生まれる。望ましい姿は、その条件集を少ない文字数へ圧縮したものではない。**現在の人間意図を、必要な要件とそれを理解するための考え方によって、直接説明している仕様書である。**

## 2. 追記と過剰な条件づけを生むという仮説

この問題を説明するために、三つの仮説を置いている。いずれも観察された出力の傾向を説明するためのものであり、モデル内部の原因として確認された事実ではない。

第一は、長い検討の文脈を引き継いだ agent が、その中で扱った細部を捨てにくくなるという仮説である。調査では、実装上の事情、却下した選択肢、特殊な失敗例などにも注意を向ける必要がある。しかし、検討に必要だった情報が、そのまま正本仕様へ残すべき情報であるとは限らない。同じ文脈の中で仕様の作成と不要な詳細の選別を担うと、詳しく調べたことや苦労して整理したことが、それ自体で仕様へ残す理由になってしまう可能性がある。

第二は、「既存仕様の編集」という作業の受け取り方が、既存の文面を保存する方向へ働くという仮説である。新しい要求は満たさなければならず、既存仕様は壊してはならず、周辺の記述を組み直すことは明確には求められていない。この組み合わせでは、既存文をすべて残して必要なことを追記する方法が、最も危険の少ない選択に見える。削除や統合には意味を失わないことの判断が必要だが、追記なら、少なくとも従来の文言は残せるからである。

この仮説では、問題はファイルに書き込めるかどうかだけではない。物理的には周辺の仕様を変更できても、それを一体として組み直すことが作業の品質として期待されていなければ、agent は変更を避ける可能性がある。「変更してもよい」という許可と、「現在の仕様を一貫した形にする責務がある」という期待は、同じではない。

第三は、矛盾のない文章を目指すことが、解釈の余地をなくすことへすり替わるという仮説である。別の読み方を想像するたびに条件を補い、反例を思いつくたびに例外を追加すれば、文章は際限なく細かくなる。しかし、同じ状況で相反する要求をしていることと、目的に沿う複数の判断が許されていることは異なる。後者まで解消すべき不備として扱うと、本来は実装者や読み手に委ねられる判断まで、仕様書が引き受けてしまう。

これらの仮説は競合しない。詳細を残したくなる文脈、既存文へ介入しにくい作業認識、解釈を閉じたくなる文章観が、それぞれ別の方向から追記を促していると考えられる。そのため、「簡潔に書く」「重複を避ける」「未定義部分を埋め尽くさない」という規則があるだけでは、十分でない可能性がある。

望ましい状態では、何を仕様として残すかを見極める視点、必要な説明のまとまりを組み直せる自由、読み手の適切な判断を信頼する文章観が、そろっている。文章を自由に書き直せても、目標が解釈の完全な封鎖のままなら、整理された長大な条件集ができる。原則を中心に書こうとしても、既存の各文が保存対象なら、条件集の言い回しを整える以上のことはできない。

## 3. 正本仕様が表しているもの

正本仕様は、現在の人間意図を表すものである。cmoc の文脈では oracle file がこれに当たり、実装を表す realization file や、仕様に至るまでの会話・調査記録とは役割が異なる。仕様として残るのは、人間が実現を求めたこと、意図的に選んだ制約、実装による違いを許容しない判断である。調査で扱った事柄をすべて保存する場所でも、実装で採用されている方法をすべて必須化する場所でもない。

ある情報が事実として正しいことと、それを規範として固定する根拠があることは別である。特定の方式が有効だったこと、ある例外を検討したこと、一般には望ましいと考えられることだけでは、その方式や例外をすべての実装が従う要求へ昇格させる理由にならない。正本仕様には、要求としての根拠がある内容が残っている。

その一方で、正本仕様は、要求を理由も文脈もない短文へ分解した集まりでもない。読み手が目的と責務を理解し、判断を適切に具体化するための説明は必要である。残すべき文脈は、その理解に寄与する文脈であり、過去の検討を再現するためだけの事情ではない。何を決めているのかと、なぜその判断が重要なのかを理解できることが、文書の簡潔さに優先する。

正本としての一貫性は、同じ要求を何度も書くことで強められるものではない。同じ概念には、その意味を担う明確な置き場所があり、関係する説明はその意味に沿ってつながっている。各所に似た規定を複製し、微妙に違う文言の関係を読み手に解読させる状態は望ましくない。参照は正本の所在を明確にするためのものであり、文章を減らす代わりに読者へ過剰な往復を要求するためのものでもない。

また、正本仕様は、変更の経緯を知らなくても自然に読める。「当初の説明を読み、その後に追加された例外を順番に適用すると、現在の仕様になる」という理解を要求しない。同じ概念の古い説明と新しい説明が並立せず、現在の状態が一つの考え方として表れている。過去の判断を追跡するための記録と、現在何が要求されているかを知るための文書が、それぞれの役割を果たしている。

この意味での最小性は、文字数の最小化ではない。必要な要件と理解のための説明が残り、根拠のない制約や同義の重複がないことである。未定義部分があること自体は欠陥ではなく、すべてを網羅するためだけに分類やファイルを増やすことにも価値はない。必要な判断を確実に伝え、それ以上の判断を不用意に固定しないことが、正本仕様の密度を高める。

## 4. 読み手が判断できる文章

望ましい文章は、対象に何が含まれるかを並べる前に、それが何であり、何のためにあるのかを説明している。共通する性質や役割が伝われば、読み手は個々の対象が同じ扱いになる理由を理解できる。適切な概念名や専門用語は、その理解を支える。専門用語を避けるために長く言い換えることも、概念による説明の代わりに対象を列挙することも、目的ではない。

例えば、障害調査に関する説明として、次のような文章がある。

> 実行ログ、通信ログ、診断ログ、スタックトレース、処理時間の記録を保持する。

人間が求めていることが障害の原因を調べられることであれば、説明の中心は次のようになる。

> 障害の原因を調べられるように、実行時の診断情報を残す。

この二つは、常に同じ仕様ではない。前者の各項目を必ず保存することが要求なら、その列挙には意味がある。後者が意図した要求であり、前者の一覧は agent が思いつくものを並べただけなら、その一覧を必須条件へ固定する必要はない。望ましい文章では、列挙を短くすることより先に、何を保証するための記述なのかが明確になっている。

列挙そのものが必要な場合もある。コマンドで受け付ける選択肢や、状態遷移に現れる状態の一覧は、要素を確定すること自体が説明の役割になり得る。条件や例外も同様であり、CLI の終了コードを呼び出し元が成功判定に使うなら、その値は正確でなければならない。望んでいるのは列挙や詳細の排除ではなく、それらが必要な判断の違いを伝えるために存在していることである。

条件を明記する価値は、それがなければ実際にどのような好ましくない判断が生じるかによって決まる。別の読み方を想像できることだけでは、補足の理由として足りない。その読み方が文脈上自然であり、避けたい判断へつながるなら、明確化には価値がある。機能の役割を理解するだけの場面で、想像可能な失敗原因をすべて書き並べることは、この必要性とは異なる。

レポートの掲載対象を説明するときにも、この違いは現れる。「解決済みの問題は含めない」「以前に報告されていても、後に解消した問題は含めない」と除外条件を積み上げるより、現在の状態を再検証して掲載するという設計意図があるなら、その原則を直接示す方が理解しやすい。

> レポートには、再検証によって現在も未解決であると確認できた問題だけを記載する。

この文章では、読み手は個々の除外条件を突き合わせるのではなく、一つの掲載原則を適用できる。再検証できない問題の扱いが運用を左右するなら、その判断は必要になる。しかし、その一点を説明することから、関連するあらゆる状況を先回りして規定する義務が生じるわけではない。また、再検証がもともと求められていない仕様へ、この例文を表現改善として当てはめれば、新しい要求を追加することになる。文章の明快さと要求の同一性は、それぞれ判断される。

例外の多さは、主文や概念の切り方が適切でないことを示す場合もある。「すべての変更を報告する」という主文に、自動整形を除く条件や、それでも影響があれば報告する条件が重なるなら、中心にある意図が「利用者が変更の影響を判断できること」ではないかという見方がある。望ましい仕様では、意図に合った原則が説明の中心にあり、強すぎる主文を多数の例外で修復する形が常態になっていない。確定済みの報告義務が、文章の都合で弱められることとも区別されている。

読み手への信頼は、中心的な意図を省略することではない。読み手に補ってもらうのは、文脈に沿う常識的なつながりや、目的を満たす具体化の仕方である。何を大切にしているのか、どの結果が必要なのかを推測させる文章は望ましくない。**意図と判断基準が伝わったうえで複数の妥当な判断が成り立つことは、文書の欠陥ではなく、適切な裁量が残っている状態である。**

その裁量が残るたびに、「この点は任意」「この場合は規定しない」という断り書きが必要になるわけでもない。余白を許可する条件を細かく列挙すれば、結局は余白の境界をすべて固定する文章へ戻ってしまう。同じ理由で、「必要」「自然」「重要」といった判断を伴う言葉の境界を、さらに網羅的な条件分岐で定めることも目標ではない。

文章の形は、こうした理解を助けるために選ばれている。一文一義、要点を先に置くこと、見出し、箇条書きは有用な手段だが、それらの形式を満たすこと自体が品質ではない。論理的につながった説明が自然な段落として読めることにも価値がある。「指定された執筆条件に従う」で足りる場面では、条件の内訳を整然と列挙しても、説明としての必要性は増えない。望ましい文章では、情報の置き方より先に、その情報をここで説明する意味が選び取られている。

## 5. 意味を守ることと、文面を固定しないこと

仕様の安定性を支えるのは、必要な要件と設計意図が維持されていることであって、既存の文章がそのまま残っていることではない。文面、見出し、記述位置、ファイルの分け方は、人間の意図を説明するための表現である。より一貫した説明になるなら、同じ意味を別の構成で表すことに問題はない。

重複した要求が一つの正本へ集まり、周辺の記述がその正本を参照していること、同じ意味の説明が統合されていること、用語や説明順が整理されていることは、意味保存と両立する。段落の統合や見出しの整理まで、実質的な設計変更と同じように扱われる状態は望ましくない。文章を自由に構成できることと、人間が決めるべきことを人間が保持していることは、両立している。

一方、明記されたアルゴリズムや必須の処理順序を削除すること、必須の列挙を単なる例へ変えること、MUST 相当の規定を MAY 相当へ弱めることは、表現の変更だけではない。仕様が許す実装の範囲を変えるからである。「読みやすくなった」「短くなった」という評価だけで、この違いが隠されることはない。

ここには、既存の意味をすべて無条件に保存すればよいという単純さもない。過去の追記によって、人間が求めていない制約が混入している場合がある。そうした記述まで保存対象にすると、意図へ立ち戻る見直しができなくなる。望ましい状態では、既存の文言に書かれているというだけで正当性が確定することも、過剰に見えるというだけで削除が正当化されることもない。人間が承認した要求と、維持すべき既存仕様を根拠として、必要な制約かどうかが判断される。

このため、承認された変更要求に基づく仕様の統合と、変更要求を持たない文章整理では、判断できることが異なる。前者では、編集前の仕様と人間の要求を照合することで、要求に根拠のない追加制約や、要求によって見直される既存の規定を判断できる。後者では、意味保存が明白な整理が中心となり、既存の方式指定を不要と断定する根拠はない。判断できない事項は、人間の設計判断を必要とする未解決事項として見えている。

説明のまとまりは、ファイルの境界と一致するとは限らない。ある概念の定義、そこから導かれる挙動、例外、関連する責務が別々の文書に分かれていても、一つの意味としてつながっている。望ましい編集の単位は、この「意味的な近傍」である。特定の一文だけが整っていても、その周辺に古い説明や矛盾する分類が残っていれば、全体として現在の仕様を説明できていない。

例えば、サブコマンドの終了状態に関する意味は、そのサブコマンドの説明だけでなく、共通の terminal result、report、failure lifecycle に関わり得る。これらは、別ファイルにあることや、一つずつ名指しされていないことによって無関係になるわけではない。一方、同じファイルにある別の機能の文章や、今回の意味に関係しない typo は、近くにあるというだけで同じ対象にはならない。

したがって、望ましい状態は、無制限な全面改稿でも、狭い箇所への場当たり的な追記でもない。必要な意味のまとまりについては現在の意図が一貫して表れ、そのまとまりから独立した意味は保たれている。**局所性は意味によって定まり、変更した行数やファイル数によって定まらない。**

小さい差分は、それ自体では品質の根拠にならない。逆に、大きく書き直したこと自体にも価値はない。人間意図の充足と影響範囲外の意味保存を前提に、関連仕様の一貫性、正本の重複の少なさ、将来の読解・レビュー負担によって、最終的な文書の良し悪しが判断される。

## 6. 人間の要求と、検討の背景が混ざらない

人間の意図を正本へ正確に表すには、何が要求であり、何が検討のための参考情報かが区別されている必要がある。検討メモの用語では、前者が `required_final_state`、後者が `supporting_context` である。

`required_final_state` は、人間が承認した、実現されるべき最終状態を表す。`supporting_context` は、調査結果や検討した選択肢、却下案、実装上の事情など、理解や検討を支える情報を表す。この分離は、要求を短く要約することではない。必ず実現されるべきことと、それを考える材料との権威の違いを明確にすることである。

人間の要求は、agent が作った要約によって、知らないうちに置き換えられていない。agent が要求と背景を整理する場合にも、要求として確定する内容は人間が確認したものである。直接与えられたユーザー指示は、その指示自体が要求の根拠となる。整理された表現が便利であることと、それが人間の意図を代表する権限を持つことは、区別されている。

仕様を構成する視点には、技術的な背景を理解する価値がある。背景情報をすべて遠ざければ、妥当な仕様を考えるための材料まで失われる。望ましい状態は、背景を利用できることと、その中の細部が自動的に必須要求へ昇格しないことが両立している状態である。

これに対して、仕様に残った内容の必要性を吟味する視点には、作成者がたどった検討からの独立性がある。人間の要求、現在の oracle、編集前の仕様との関係、意味的な近傍にある既存の正本を根拠として、その記述が必要かどうかを判断できる。調査や TUI の会話履歴、作成者の説明や推論、実装上の都合を再び大量に読むことによって、同じ細部へ引き戻される構成にはなっていない。

ここでいう fresh context は、新しい session を使っているという形式だけを指さない。何を判断材料にするかが分離されていることである。作成時の背景をすべて再投入していれば、別の session でも同じ保存圧力を受ける可能性がある。逆に、作成者の説明を読まないことは、判断に必要な正本まで読めないことを意味しない。人間の要求と関連仕様への到達可能性は保たれている。

構成する役割と吟味する役割は、品質目標を分担して片方を弱める関係ではない。main agent が作る仕様にも、最初から一貫した現在状態としての品質が求められている。reduction agent は、雑な追記を前提とした清掃担当ではなく、別の文脈から見ても、その説明と制約が必要であるかを吟味する安全網である。

また、吟味の対象は、main agent が直接変更した文字列だけではない。同じ意味的な近傍に残る旧記述、重複、不要な例外、分散した正本責務も、最終的な説明の一貫性に関わる。両者は同じ意味のまとまりを見ており、無関係な改善へ広がらない境界も共有している。必要な要件と設計意図を守ることについて、どちらの役割にも例外はない。

## 7. 不足と過剰の双方を抑える品質保証

仕様の品質は、要求が抜けていないことだけでは成立しない。人間が要求していないことまで固定していないことも、同じく重要である。望ましい検証には、coverage と excess という二つの視点があり、それぞれが独立した文脈から最終仕様を評価している。

Coverage の視点では、人間が承認した要求が満たされ、維持すべき既存仕様が失われていないことが確かめられている。必要な目的、非目標、失敗時の挙動、責務の境界も、その意味が保持されている。しかし、これは旧文面が残っているかを照合する検証ではない。要求が認める意味変更を踏まえながら、最終状態として何が保証されているかを見る検証である。

Excess の視点では、人間の要求や既存の正本に根拠のない規範的内容が残っていないことが確かめられている。参考情報が必須条件へ変わっていないこと、実装方式が不必要に固定されていないこと、同義の要求が複数の場所で別々の正本のように振る舞っていないことが、この視点に含まれる。必要なことを満たすために、不要なことまで約束させる仕様になっていないことが重要である。

この二つの検証は、編集担当者や削減担当者の自己申告だけには依存しない。「意味を維持した」という説明があることと、独立して要求保持を確認できることは異なる。検証の役割は読み取り専用であり、判定しながら成果物を変更して、自分の判定対象を曖昧にすることもない。

検証が重視するのは、人間が要求したことの coverage であって、想像可能な状況の網羅ではない。原則から必要な判断ができるなら、その判断を別の文で繰り返していないことは欠落ではない。「現在も未解決であると確認できた問題だけを掲載する」と定まっているとき、解決済みの問題を除くという文言が別にないことだけでは、不適合の理由にならない。

執筆とレビューは、この点で同じ文章観を共有している。執筆では裁量を認め、レビューでは裁量の残る箇所をすべて欠陥として扱う、という関係にはなっていない。中心的な意図が伝わるか、残された余地によって実際にどの判断が困るか、その余地は目的に沿って判断するためのものかが問われる。

安全性に関しては、短さより要求欠落の回避が優先される。意味保持を確認できない削減や、coverage に問題がある削減が、文章がすっきりしたという理由で採用されることはない。吟味前の candidate が安全側の境界として残っており、不確実な削減を採用せずに済む。過剰な記述だけが残る場合も、その改善が際限のない自動反復にならず、残る課題は未解決事項として把握できる。

したがって、望ましい最小化は、何が何でも小さい出力を作る仕組みではない。要求保持を損なわずに、必要性の説明できない制約や重複を取り除ける仕組みであり、判断できないときには、その不確実性が結果の中で正直に扱われている。

## 8. スキルと正本が共有する価値観と、それぞれの責務

`maintain-software-specifications` は、人間の要求と設計意図を、読み手が理解して判断できる正本仕様として保つためのスキルである。何を要求として残すかの選択から、関連する説明の再構成、文章表現、完成した仕様の確認までを、一つの編集責務として扱う。対象の意味と役割を説明し、必要な区別を選び、段落や節のまとまりとして説明の筋を明らかにする判断を助ける。

そのため、形式的な規則は目的を達成する手段として位置づけられている。「三項目以上なら箇条書き」といった境界を満たすことや、分けられる文をすべて分けることが、文章の合否を決めるわけではない。文章に関する規範には、読み手がどのように理解することを目指しているのかという短い理由があり、少数の対比例によって判断の方向が分かる。

対比例は、不要な列挙や条件を取り除く例だけでなく、必要な列挙や条件が残っている例も含む。そうすることで、好ましさが特定の語の不在や見た目の単純さではなく、必要な意味が適切に伝わることにあると分かる。例の目的は、考えられる文章のパターンを網羅することではない。

仕様の内容選択と文章の構成は、同じ要求を根拠に判断される。例えば、列挙を原則へまとめてよいかは、その一覧が保証する契約なのか、理解を助ける例なのかによって変わる。重要な人間意図へ集中し、適切な裁量を残すという考え方を、その意図が伝わる説明まで一貫して適用する。正本仕様の新規作成・改訂・意味を保った推敲を対象とし、日本語固有の指針も、日本語の仕様を記述するために使う。

仕様の意味を決める authority は、利用者の要求と対象リポジトリの正本にある。cmoc の意味仕様や受理条件は、cmoc の oracle doc／oracle src に置かれている。installed skill の有無によって、何が要件であるか、どの意味変更が許されるか、何をもって適合とするかが変わることはない。スキルは、その意味を適切に理解し表現するための補助である。

共通の方針には、意味保存と文面保存の違いが明確に表れている。そのうえで、各役割が持つ権限と品質責務が区別されている。人間の変更要求を統合する役割と、要求を持たない意味保存型の整理と、読み取り専用のレビューが、同じ範囲の設計判断を持つわけではない。共通の文章観があることは、すべての操作へ自由な仕様変更権限を与えることを意味しない。

## 9. 人間が信頼して判断できる編集結果

広い意味のまとまりを扱えることは、その結果が信頼できる形で区切られていることと組み合わさっている。望ましい編集環境では、編集前の状態、人間が承認した要求、構成担当が作った candidate、吟味された final が区別できる。もともと存在した未コミット差分と今回の編集が混ざり、何を評価しているのか、どこまで取り消せるのかが分からなくなる状態ではない。

run worktree の隔離や candidate の checkpoint が担う意味は、再構成の自由を安全に支えることである。candidate は、人間にもう一段階のレビューを課すための成果物ではなく、削減の意味保持を確認できないときに、その削減を採用せずに済む境界である。編集結果を採用するか、採用しないかの判断が、他の作業へ不用意に影響しない。

結果の信頼性には、意味に関する判断と、機械的に確かめられる事実の両方が関わる。意味を本当に保存したかを Git の差分だけで決定することはできない。しかし、報告された `changed_paths` と実際の変更が一致しているか、検証が読み取り専用であったか、採用可能な結果が対応する commit として確定しているかは、曖昧な説明に委ねる必要がない。

仕様だけを扱う役割では、realization file や保護対象の `INDEX.md`、`AGENTS.md` が変更されていないことも、その境界に含まれる。削減を採用しない場合に candidate と一致する状態を確保できること、report の commit や変更箇所が実際の Git 状態と一致することも、結果への信頼を支える。

一方、変更対象の適切さは、「構成担当が触ったファイルの部分集合か」という機械的な条件だけでは表せない。意味的な近傍の再構成では、構成担当が直接変更していなかった関連仕様も関わり得る。保護対象や実差分の一致を機械的に確かめることと、変更が人間の要求に関係する範囲かを意味として判断することが、混同されていない。

規範的内容の根拠を追跡できることも重要である。新たに残った規範的内容が、人間の要求のどこ、あるいは既存 oracle のどこに支えられているかを確認できる。削除された内容についても、重複だったのか、根拠のない制約だったのか、冗長な説明だったのか、要求されていない実装詳細だったのかが分かる。この対応関係は、検証を助ける一時的な Structured Output として表現できる。

その記録は、新しい正本仕様ではない。根拠が形式上割り当てられていることや参照先が実在することは機械的に確かめられるが、根拠が意味的に妥当であることは別の判断である。対応表があるだけで正しさが証明されたことにはならず、対応表の作成者が新しい要求を決める権限を得るわけでもない。

また、この追跡可能性のために、正本全体が専用の DSL で表現されていることは必要条件ではない。人間が読む仕様書と、検証に必要な構造化情報は役割が異なる。望むのは、要求と記述の関係が検証できることであって、すべての意味を機械判定可能な記法へ閉じ込めることではない。

人間向けの出力にも、同じ情報選択の考え方が表れている。人間が通常確認する中心は、最終的な仕様とその差分、検証の結果、判断が必要な未解決事項である。どこが変更され、削減が行われたか、要求保持と過剰規定の検証がどう評価したか、結果を採用するか採用しないかを判断するための情報が見えている。

削除した一文ごとの説明や verifier の全文は、必要なときに追跡できる記録として残っているが、通常の report を埋め尽くしていない。正本から減らした説明を、毎回読むことが前提の巨大な報告へ移しただけでは、人間の負担は減らない。詳細な追跡可能性と、日常的な確認の簡潔さが両立していることが望ましい。

## 10. 望ましい状態の判断基準

このビジョンで重視するのは、今回何行変わったかではなく、人間が今後その仕様を理解し、判断し、維持するために負担する総コストである。人間の要求を満たすことと、要求の影響範囲外の意味を保つことが前提にあり、そのうえで、関連仕様が一貫し、正本責務が重複せず、不要な条件を読み解く必要が少ない状態を望んでいる。

AI が文章の書き直しを引き受けられても、人間による意味の確認が不要になるわけではない。そのため、毎回広範な美化が行われることも、最小の差分へ固執して複雑さを先送りすることも、理想ではない。必要な意味のまとまりが素直に説明され、その理解に関係しない変更の確認まで要求されないことに価値がある。

品質の評価には、要求の欠落や意図しない意味変化がないことに加えて、人間がレビューに要する時間や追加修正の負担が関わる。同じ概念を理解するために何箇所を読む必要があるか、同じ要求がどれほど重複しているか、根拠のない規範文が残っていないかは、文書の認知負荷を捉える手がかりになる。

文字数や byte 数、追加された規範文と削除・置換された規範文の量、「ただし」「除く」「場合」といった語の増減も、傾向を見る材料にはなる。しかし、固定の削減率や特定の語の有無が、そのまま合否にはならない。必要な列挙や境界が残ることは成功であり、短くするために独立した要求を失うことは失敗である。

最終的に望むのは、読み手が過去の編集の経緯をたどらずに、現在何が求められているかを理解できることである。明示すべき判断は明示され、個別の場面へ適用できる原則があり、適切な裁量が残っている。文章を書く側、吟味する側、検証する側が、この状態を同じ意味で良いものとして評価している。

その仕様書には、必要な要件と設計意図を守る強さと、それらを表す文章を固定しない柔軟さがある。人間の意図を説明するための正本が、過去の対処を保存するための条件集になっていない。**より少ない原則で、より多くを理解できること。そして、何を決めたのかだけでなく、何を理解して判断すればよいのかが伝わること。**それが、仕様書とそれを支える編集の仕組みに求める姿である。
