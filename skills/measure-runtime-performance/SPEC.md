# 実行時間を計測するスキルの仕様

## 目的と適用場面

性能についての判断を、比較可能な実測値に基づける。性能調査や改善、benchmark の保守、性能要件の検証に適用する。通常の開発では、変更による処理量や待ち時間への影響を判断する必要がある場面で使う。配布設定では暗黙の適用を有効にする。

## 必要な観測を選ぶ

利用者の要求とリポジトリの性能要件を確認する。
ただし、要件がない場合は、比較可能な baseline や既存 benchmark、観測したばらつきから判断する。
一般論だけで新しい性能要件を作らない。

利用者が待つ処理、または変更の影響を観測できる代表経路を選ぶ。
そのうえで、入力規模と実行環境を記録し、起動や I/O を含む範囲を明らかにする。
内部関数の計測だけでは利用者の待ち時間を説明できない場合は、全体の経路も観測する。

既存の計測手段を優先し、判断に必要な観測が得られるかを確かめる。不足する場合は、計測の信頼性と保守負担に合うツールを開発依存へ追加する。また、独自の補助処理で専用ツールの機能を再実装する負担も考慮し、依存管理と実行権限は対象リポジトリに従う。

## 比較できる値を取る

既存実装では変更前の正しく動作する版を baseline にし、同じ条件で変更後を計測する。
ただし、安全に baseline を取得できない場合は、絶対時間と比較できない理由を報告する。
一方、新規実装では、最初に正しく動いた版を追加最適化の baseline にする。

wall-clock time は monotonic clock または同等の計測手段で測る。
反復回数と実行上限は、正常時の所要時間、ばらつき、実行コストから決める。
安価に反復できる処理では、warm-up と測定を分け、個別値と代表値・ばらつきを確認する。
また、停止や異常な待機を打ち切れる方法を用意し、上限到達時は下限値として記録して原因を調べる。

破壊的な処理や外部作用を伴う計測は、許可された範囲で行う。
無断で本番負荷や課金を増やさない。
反復や計測ができない場合は、その制約を報告する。

## 原因を確かめて改善する

測定結果を要件、baseline、利用場面に照らし、改善が必要な問題があれば区間計測や profiler で原因を調べる。その際、外部サービスの待機とアプリ自身の計算を切り分け、実測上の支配的な原因を改善対象にする。

修正では、確認した問題に関係する実装を組み直し、出力と重要な副作用を保つ。変更後は profiler なしの同じ条件で比較し、必要なテストと品質ゲートを実行する。その際、差は測定のばらつきを踏まえて判断し、要求を満たしたところで改善を終える。

## 検査と報告を保守する

継続的な性能検査は、要件や再現可能な回帰、既存の benchmark 運用に基づいて追加する。
閾値には観測したばらつきを考慮する。
ただし、停止検出用の timeout を、性能が良いことの根拠にしない。

複数の規則が同じ計測を求める場合は、条件をそろえて結果を共用する。

報告は、どの経路をどの条件で測り、絶対時間と比較結果から何を判断したかが分かる説明にする。また、調査やツール追加の理由を判断へ結び付け、未計測の範囲も明らかにする。詳細な記録があれば、要点と参照先を示す。

評価では、主張を実測値へたどれること、比較条件と正しさが保たれていることを確認する。
