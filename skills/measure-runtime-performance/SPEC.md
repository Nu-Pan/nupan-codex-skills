# 実行時間を計測するスキルの仕様

## 目的と適用場面

性能についての判断を、比較可能な実測値に基づける。性能調査や改善、ベンチマークの保守、性能要件の検証に適用する。また、通常の開発でも、変更による処理量や待ち時間への影響を判断する必要がある場面で使う。配布設定では暗黙の適用を有効にする。

## 必要な観測を選ぶ

利用者の要求とリポジトリの性能要件を確認する。要件がない場合は、比較の基準となる測定結果（ベースライン）や既存のベンチマーク、観測したばらつきから判断する。一般論だけで新しい性能要件を作らない。

利用者が待つ処理、または変更の影響を観測できる代表的な処理経路を選ぶ。そのうえで、入力規模と実行環境を記録し、計測に起動や I/O を含むか、どこからどこまでを測るかを明らかにする。内部関数の計測だけでは利用者の待ち時間を説明できない場合は、全体の経路も観測する。

既存の計測手段を優先し、判断に必要な観測が得られるかを確かめる。不足する場合は、計測の信頼性と保守負担に合うツールを開発依存へ追加する。また、独自の補助処理で専用ツールの機能を再実装する負担も考慮し、依存管理と実行権限は対象リポジトリに従う。

## 比較できる値を取る

既存実装では、変更前の正しく動作する版をベースラインにし、同じ条件で変更後を計測する。ただし、安全にベースラインを取得できない場合は、計測した所要時間と、変更前と比較できない理由を報告する。一方、新規実装では、最初に正しく動いた版を、その後の最適化を評価するベースラインにする。

実際の経過時間は、単調時計（monotonic clock）または同等の計測手段で測る。反復回数と実行時間の上限は、正常時の所要時間、ばらつき、実行コストから決める。安価に反復できる処理では、ウォームアップと測定を分け、個々の測定値、代表値、ばらつきを確認する。

また、停止や異常な待機を打ち切れる方法を用意する。実行時間が上限に達した場合は、その値を所要時間の下限として記録し、原因を調べる。

破壊的な処理や外部への作用を伴う計測は、許可された範囲で行い、無断で本番環境への負荷や課金を増やさない。反復や計測ができない場合は、その制約を報告する。

## 原因を確かめて改善する

測定結果を要件、ベースライン、利用場面に照らし、改善が必要な問題があれば、区間ごとの計測やプロファイラーで原因を調べる。その際、外部サービスの待機とアプリ自身の計算を切り分け、実測で所要時間への影響が大きかった原因を改善対象にする。

修正では、確認した問題に関係する実装を組み直し、出力と重要な副作用を保つ。変更後は、プロファイラーを使わずに変更前後を同じ条件で比較し、必要なテストと品質ゲートを実行する。その際、測定値の差はばらつきを踏まえて判断し、要求を満たしたところで改善を終える。

## 検査と報告を保守する

継続的な性能検査は、要件や再現可能な性能回帰、既存のベンチマークの運用に基づいて追加する。その際、閾値には観測したばらつきを考慮する。なお、停止検出用のタイムアウトは、性能が良いことの根拠にはしない。

複数の規則が同じ計測を求める場合は、条件をそろえて結果を共用する。

報告では、計測した経路と条件を示し、所要時間と比較結果から何を判断したかを説明する。また、調査やツールの追加によって何を確かめる必要があったかを説明し、未計測の範囲も明らかにする。詳細な記録があれば、要点と参照先を示す。

評価では、判断の根拠となる実測値をたどれるか、比較条件と処理の正しさが保たれているかを確認する。
