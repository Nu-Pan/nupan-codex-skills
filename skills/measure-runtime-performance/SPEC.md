# measure-runtime-performance の仕様

## 目的

このスキルは、実行可能な処理の実行時間を計測し、確認したボトルネックを改善する作業に適用する。
実行時間に関する判断と主張を、コードの見た目や推測ではなく実測値に基づかせる。

根本原則を次に示す。

> 実行時間を推測しない。計測する。

変更後の状態は、次の条件を満たす。

- 利用者が実行する代表的な処理経路を計測している。
- 比較に使用する計測条件が揃っている。
- 改善対象が、計測または profiler の結果から特定されている。
- 変更前後の正しさが維持されている。
- 改善結果が、同じ条件で再計測されている。
- 計測できない範囲と性能上の未検証事項が明示されている。

このファイルは、`measure-runtime-performance` のスキル仕様の正本である。
実行時仕様を変更するときは、先にこのファイルを変更する。

## 適用条件

実行可能な処理経路を作成または変更する場合に、このスキルを使用する。
言語、実行形式、テストフレームワークは問わない。

対象となる処理経路には、次の内容を含む。

- CLI と補助スクリプト
- batch、job、build、変換処理
- server endpoint と request handler
- library の公開操作と主要な内部処理
- test、benchmark、fixture の実行経路

性能改善、低速化の調査、性能回帰の確認、benchmark の作成または変更を依頼された場合も使用する。
スキル名が明示されていない場合も使用する。

暗黙の適用を有効にするため、配布物は次の条件を満たす。

- `SKILL.md` の description に、実行可能な処理の作成、変更、調査、性能比較を記述する。
- `SKILL.md` の description に、スキル名が明示されていない場合も使用することを記述する。
- `agents/openai.yaml` の `policy.allow_implicit_invocation` を `true` にする。

## 対象外

このスキルだけでは、次の作業を行わない。

- 利用者または正本仕様が定めていない性能要件の新設
- 静的なコード確認だけに基づく実行時間の断定
- 実測した問題がない処理への先回りした最適化
- 許可されていない本番負荷試験または外部サービスへの反復 request
- 正しさ、安全性、互換性を損なう高速化
- 計測のためだけに行う永続的な依存関係や公開面の追加

文書、型注釈、静的設定だけを変更し、実行時の処理経路が変わらない作業には適用しない。
実行時間以外の CPU 使用量、memory 使用量、throughput は、利用者または正本仕様が求める場合だけ主対象にする。

## 用語

### 代表経路

代表経路は、利用者が実際に行う操作、または変更した処理を外部から実行できる最も近い経路である。
内部関数だけを計測しても利用者の待ち時間を表せない場合は、end-to-end の経路を優先する。

### baseline

baseline は、変更後の結果と比較するために変更前または最初の正常動作時に取得する計測値である。
既存実装では、変更前の現在の worktree を原則として baseline にする。
新規実装では、最初に正しく動作した最小実装を baseline にする。

### 調査開始条件

調査開始条件は、詳細な区間計測または profiler を開始するための条件である。
調査開始条件は、性能要件または合否基準ではない。

## 入力と優先順位

計測前に確認する入力を次に示す。

- 利用者が求める操作と性能要件
- 対象リポジトリの正本仕様と性能検証方法
- 変更対象となる処理経路
- 代表的な入力と入力規模
- 実行 command、環境、build mode、cache 状態
- 副作用、外部接続、費用、秘密情報、実行権限

性能の判定根拠には、次の優先順位を適用する。

1. 利用者または正本仕様が定める明示的な性能要件を使用する。
2. 同じ条件で取得した変更前の baseline を使用する。
3. 対象リポジトリが管理する既存 benchmark の実測値を使用する。
4. 同じ条件で反復した計測値と、そのばらつきを使用する。

一般論や予想だけで、未定義の性能要件を補わない。
対象リポジトリが計測方法を定めている場合は、その方法を優先する。

## 実行時の規則

### 性能を実測値で判断する

- コードの行数、loop の形、計算量の予想だけで、処理が速いまたは遅いと断定しない。
- test の成功、timeout への未到達、静的解析の成功を、性能の根拠にしない。
- 改善率を、比較可能な変更前後の実測値なしに報告しない。
- 計測値の差が観測したばらつきに収まる場合は、改善または回帰と断定しない。

### 代表経路と計測条件を決める

- 変更した処理を通る代表経路を選ぶ。
- 実際の利用に近く、再現可能で、安全に実行できる入力を選ぶ。
- 入力の件数、byte 数、file 数など、実行時間へ影響する規模を記録する。
- 比較では、command、入力、環境、build mode、cache 状態を揃える。
- startup、setup、I/O、外部待ちを含むかを明示する。
- 複数の経路がある場合は、変更した経路と利用頻度の高い経路を優先する。

### baseline を取得する

- 既存実装を変更する前に、現在の worktree で baseline を取得する。
- baseline の出力または副作用が正しいことを確認する。
- 新規実装では、最初に正しく動作した版を追加最適化前の baseline にする。
- 変更前を安全に実行できない場合は、無理に過去版を復元しない。
- baseline を取得できない場合は、理由を記録して絶対時間だけを報告する。

### 実行時間を計測する

- 対象リポジトリに benchmark tool がある場合は、その tool を使用する。
- tool がない場合は、wall-clock time を monotonic clock または同等の仕組みで計測する。
- 最初の実行には、停止や異常な待機を打ち切れる安全上限を設ける。
- 明示された上限がない小規模な local 処理では、10 秒を診断用の既定上限にする。
- 上限に達した場合は、その値を実行時間の下限として記録する。
- 上限に達した処理を、原因調査前に無条件で反復しない。

安価で反復可能な処理では、次の方法でばらつきを確認する。

1. 必要な warm-up を計測対象と分けて実行する。
2. 同じ条件で 3 回以上計測する。
3. 個別値と中央値を記録する。
4. 最小値と最大値、または同等のばらつきを確認する。

timer の分解能に近い短い処理では、同じ操作を一回の計測内で複数回実行する。
反復回数で割った値を、一回当たりの時間として扱う。

高コスト、非決定的、または副作用のある処理を機械的に反復しない。
反復できない場合は、計測回数と比較上の制約を報告する。

### 詳細調査を開始する

次のいずれかを確認した場合は、区間計測または profiler で時間の内訳を調べる。

- 明示的な性能要件を満たしていない。
- baseline より遅く、差が計測値のばらつきを超えている。
- 既存 benchmark が示す許容範囲を外れている。
- 最小の有効入力を扱う network に依存しない local 処理が 1 秒以上かかる。
- 診断用の実行上限に達した。

1 秒は、未定義の性能要件を補う合否値ではない。
1 秒は、秒単位の待機を放置せずに内訳を確認するための調査開始条件である。

### ボトルネックを特定する

- end-to-end の時間を、startup、setup、計算、I/O、外部待ちなどの区間へ分ける。
- profiler、trace、計測 log などから、時間を実際に消費している区間を特定する。
- 一見遅そうな箇所ではなく、実測上の支配的な箇所を改善対象にする。
- 外部サービスの待ち時間と first-party code の処理時間を分ける。
- 外部要因が支配的な場合は、first-party code の高速化として報告しない。

### 改善して再計測する

1. baseline の出力と重要な副作用を保存する。
2. 確認したボトルネックへ最小の変更を加える。
3. focused test または同等の検証で正しさを確認する。
4. baseline と同じ条件で実行時間を再計測する。
5. full test と対象リポジトリの品質ゲートを実行する。
6. 絶対時間と比較結果を整理する。

正しさを保てない変更は採用しない。
明示的な性能要件を満たした場合は、追加の最適化を必須にしない。
改善幅がばらつきを超えない場合は、効果が確認できない変更として見直す。

### 性能回帰を検証する

性能に関する永続的な test または benchmark は、再現可能な根拠がある場合だけ追加する。
追加を検討できる根拠を次に示す。

- 正本仕様に定量的な性能要件がある。
- 大きな性能回帰を安定して再現できる。
- 対象リポジトリが性能 benchmark を品質ゲートとして管理している。

wall-clock time の assertion には、同じ環境で観測したばらつきより十分に大きい余裕を持たせる。
共有 CI で安定しない厳密な時間 assertion を通常の機能 test へ追加しない。
timeout は停止検出として扱い、処理速度の合格を示す benchmark として扱わない。

### 安全に計測できない場合を扱う

- 破壊的または非 idempotent な処理を、確認なしに反復しない。
- 本番環境、課金対象、外部サービス、秘密情報が必要な計測を、権限なしに実行しない。
- 計測環境がない場合は、再現に必要な command、入力、前提条件を示す。
- 計測していない経路を、性能確認済みとして報告しない。
- 計測不能を、推測値で埋めない。

## 出力

最終報告では、性能判断を再現できる情報を簡潔に示す。
報告する情報を次に示す。

- 計測した代表経路
- command、入力規模、重要な環境条件
- baseline と変更後の絶対時間
- 反復回数、中央値、確認したばらつき
- 特定したボトルネックと変更内容
- 正しさの検証結果
- 計測できなかった範囲と比較上の制約

利用者が性能改善を主目的としていない場合は、実行時間と計測条件を一行程度に要約してよい。
比較可能な baseline がない場合は、改善率を示さない。

## 検証

完了前に、次の条件を確認する。

- 変更した実行可能な処理について、代表経路を計測している。
- 計測できない処理には、具体的な理由がある。
- 性能上の判断が、実測値または profiler の結果に基づいている。
- baseline と変更後で、比較に必要な条件が揃っている。
- 計測値のばらつきを無視して改善または回帰を断定していない。
- 実測したボトルネック以外を、推測だけで最適化していない。
- 変更前後の出力と重要な副作用が一致している。
- timeout の成功だけを、処理速度の根拠にしていない。
- 最終報告に、絶対時間と計測条件が含まれている。
- 未計測の範囲を、性能確認済みとして報告していない。

1 つでも満たさない場合は、完了としない。

## 重視する価値

実行時間は、コードを読むだけでは確定できない。
処理系、入力、I/O、cache、外部待ち、実行環境によって結果が変わるためである。

実測を先に行うことで、推測による過剰な最適化と、明白な遅延の放置を同時に避ける。
定量的な要件がない場合も、調査開始条件によって秒単位の異常な待機を可視化する。
