# スキルの仕様

## 目的

このスキルは、AI が日本語の技術文書を作成または変更するすべての作業に適用する。
読み手が要点と情報の関係を速やかに把握できる文章を作る。

作成または変更後の文章は、次の状態を満たす。

- GitHub Flavored Markdown（GFM）で書かれている。
- 一文一義で書かれている。
- 見出しと箇条書きで構造化されている。
- 文章全体と各節の要点が、詳細より先に示されている。
- 要点を支える詳細が、対応する要点の後にある。
- 三項目以上の列挙では、その列挙が何を示すかが先に示されている。
- 正確性または簡潔さが高まる場合は、技術用語が使われている。

このファイルは、スキル仕様の正本である。
規則を変更するときは、先にこのファイルを変更する。

## 適用条件

日本語の技術文書を扱う文章作業では、このスキルを使用する。
対象となる文章作業を次に示す。

- 新規作成
- 追記
- 改訂
- 推敲
- リライト

対象となる技術文書には、次の文書を含む。

- 仕様書
- 設計書
- README
- 手順書
- Issue の説明
- Pull Request の説明

文章作業が利用者の依頼の主目的であるか、実装や調査などに付随する作業であるかを問わない。
利用者がスキル名や推敲を明示していない場合も、このスキルを使用する。

暗黙の適用を有効にするため、配布物は次の条件を満たす。

- `SKILL.md` の description に、対象となる文章作業と技術文書を記述する。
- `SKILL.md` の description に、スキル名が明示されていない場合も使用することを記述する。
- `agents/openai.yaml` の `policy.allow_implicit_invocation` を `true` にする。

文章規則は、文書を作成または変更する時点で適用する必要がある。
明示的な呼び出しを必要とすると、通常作業に付随する文書の更新へ規則を適用できないためである。

## ファイルの責務

### `SPEC.md`

`SPEC.md` は、スキルの規則とその理由を定義する。

次の情報を書く。

- スキルの適用条件
- 暗黙の適用に必要な配布設定
- `SKILL.md` に含める規則
- `SKILL.md` に含めない情報
- 規則の根拠
- 規則の前提条件
- 規則が重視する価値

### `SKILL.md`

`SKILL.md` は、スキルの使用時にエージェントが従う規則だけを示す。

次の情報を書く。

- スキルの適用条件を示す YAML frontmatter
- 入力を扱うときの優先順位
- 文章の判定基準
- 文章を作成または変更する手順
- 出力の既定形式
- 出力前の確認項目

次の情報は書かない。

- 規則を採用した経緯
- 規則の根拠や背景
- リポジトリの保守手順
- インストール手順
- 未確定の仮置き項目

## 優先順位

利用者の明示的な指示を、このスキルの既定の規則より優先する。
利用者が文章に関する条件を指定した場合は、その条件に従う。

明示的な指示がない部分には、この仕様の規則を適用する。
利用者の依頼を実現するために必要な場合は、文章の意味や事実関係を変更する。
文章規則の適用だけを理由として、利用者が変更を求めていない意味や事実関係を変えない。

## 判定基準

文章に適用される規則をすべて満たしているかを確認する。
利用者の明示的な指示による例外は、違反とみなさない。

次のいずれかに該当する文章は、規則を満たさない。

- GFM で構造化できる情報が、平文のまま記述されている。
- 1 文に、独立して述べられる複数の内容がある。
- 複数の話題が、見出しなしで連続している。
- 並列する情報が、箇条書きなしで連続している。
- 要点より先に、要点を支える詳細が列挙されている。
- 三項目以上の列挙について、その列挙が何を示すかが事前に示されていない。
- 読み手が、個別項目から文章全体の要点を推測する必要がある。

形式上の条件を満たしていても、利用者が変更を求めていない意味や事実関係が変わっていれば規則に適合しない。

## 入力と前提

### 必要な入力

日本語の技術文書を作成または変更する依頼を入力とする。
既存の文書を変更する場合は、その文書も入力とする。

次の情報が与えられている場合は、制約として扱う。

- 文章の目的
- 想定する読み手
- 文体と語調
- 出力形式
- 変更を禁止された語句や表記

不足した情報は、入力から明確に判断できる範囲だけを補う。
判断できない事実は追加しない。

### 保護する情報

既存の文書を変更する場合は、利用者が変更を求めた範囲を除き、次の情報と表記を変更しない。
新しい文書を作成する場合は、利用者から与えられた次の情報と表記を維持する。

- 入力の意味と主張
- 事実関係
- 固有名詞
- 数値
- 日付
- 技術用語
- 引用
- 出典
- リンク
- コード
- コマンド
- 利用者が指定した文体と語調

入力に含まれる技術用語は維持する。
技術用語によって正確性または簡潔さが高まる場合は、技術用語を使う。
一般語への言い換えによって意味や簡潔さが損なわれる場合は、言い換えない。

外部の事実確認は、このスキルの標準作業に含めない。
事実確認を依頼された場合は、文章の作成や変更とは別の作業として扱う。

## 文章の規則

### GFM で書く

作成または変更後の文章は、GFM で書く。
GFM の記法を意味に応じて使い分ける。
たとえば、見出しや箇条書きを使う。
必要な場合は、コードブロックも使う。

GFM を採用する理由は、文章の論理構造を明示できるためである。
読み手にもエージェントにも、構造を走査しやすい形式である。

利用者が別の形式を明示した場合は、その形式を優先する。

### 一文一義にする

一文一義とする。
1 つの文では、1 つの主要な内容だけを述べる。

ここでいう内容とは、単独の文として自然に述べられる意味の単位である。
文字数だけでは判定しない。

単独の文として自然に成立する内容は、別の単位として扱う。
複数の述語があるだけでは分割しない。
各述語が独立した内容を担う場合は、原則として分割する。

1 つの文に複数の主要な内容がある場合は、複数の文に分割する。
分割後も関係が分かるように、近接配置や階層構造を使う。

1 つの文に内容を詰め込むより、複数の文や箇条書きへ分割する。
この分割は、走査と差分確認を容易にする。

文を分割しても、論理関係は失わない。
分割によって、不自然な断片文を増やさない。

### 見出しと箇条書きで構造化する

複数の話題がある場合は、見出しで分ける。
同種の複数の項目は、箇条書きで並べる。

順序に意味がある場合は、番号付きリストを使う。
順序に意味がない場合は、箇条書きを使う。

見出しの親子関係は、内容の包含関係と一致させる。
箇条書きの各項目には、同じ粒度の情報を置く。

構造化の目的は、情報の関係を目で追えるようにすることである。
装飾のためだけに、不要な階層を増やさない。

### 要点を詳細より先に置く

文章全体と各節では、要点を先に述べる。
要点を支える詳細は、対応する要点の後に置く。

要点を支える情報には、次の種類がある。

- 内訳
- 適用範囲
- 定義
- 例
- 背景情報

複数の項目を列挙する場合は、その列挙が何を示すかを先に述べる。
個別項目は、導入文に続く箇条書きとして示す。

情報を組み立てるときは、次の順序を基準とする。

1. 要点
2. 情報の位置づけ
3. 詳細や内訳
4. 定義
5. 例や背景情報

すべての段階が必要とは限らない。
必要な段階だけを使う。

見出しや箇条書きを使えない場合は、要点が分かる文を先に置く。
適用範囲や内訳は、その文末の括弧内に置く。

利用者が見出しや箇条書きを禁止した場合も、要点を省略しない。
列挙が何を示すかを、先に一文で述べる。
個別項目は、その文末の括弧内に置く。

この順序は、読み手の推論負荷を下げる。
読み手に、個別項目から文章全体の要点を推測させてはいけない。

#### 例

規則を満たさない例では、個別項目を先に置いている。

> Ubuntu 24.04、macOS 15、Windows 11 をサポートします。

改善例では、列挙が何を示すかを先に述べている。

> 三つの OS をサポートします。
>
> - Ubuntu 24.04
> - macOS 15
> - Windows 11

見出しや箇条書きを使えない場合は、個別項目を文末の括弧内に置く。

> 三つの OS をサポートします（Ubuntu 24.04、macOS 15、Windows 11）。

### 列挙が何を示すかを先に述べる

本文で三項目以上を列挙する場合は、その列挙が何を示すかを個別項目より先に述べる。

先行する文には、列挙の位置づけまたは文の要点を含める。
個別項目は、後続の箇条書きとして示す。
見出しや箇条書きを使えない場合は、個別項目を文末の括弧内に置く。

「次の項目」のような語句だけでは、列挙の内容を示したことにならない。
内容を示さない導入文を、列挙の説明として使わない。

短い二項の並列には、この規則を適用しない。
二項まで一律に分割すると、文章が冗長になるためである。

この規則は、作成または変更する本文に適用する。
原文どおり残す必要がある箇所には適用しない。
規則を適用しない箇所を次に示す。

- 引用
- コードやコマンド
- 変更を禁止された名称や語句
- 利用者が原文どおりの表記を求めた箇所

利用者が列挙の順序を明示した場合は、優先順位の規則に従う。

日本語では、述語が文の末尾に置かれることが多い。
列挙を先に置くと、読み手は複数の項目を作業記憶に保持したまま述語を待つ必要がある。

この規則は、列挙による作業記憶の負荷を抑えるために設ける。
要点を詳細より先に置く規則とは、独立して判定する。

#### 例

規則を満たさない例では、執筆条件を列挙してから結論を述べている。

> 目的、想定読者、文体、出力形式が指定されている場合は、その指定に従います。

改善例では、結論と列挙の位置づけを先に述べている。

> 指定された執筆条件に従います。
>
> 執筆条件には、次の情報が含まれます。
>
> - 目的
> - 想定読者
> - 文体
> - 出力形式

## 文章作業の手順

### 1. 入力条件を確定する

利用者の明示的な指示を抽出する。
作成または変更する文書を特定する。
維持する情報と表記を特定する。

### 2. 必要な内容を確定する

利用者の依頼を実現するために必要な内容を特定する。
既存の文書を変更する場合は、変更する内容と維持する内容を分ける。

### 3. 内容を構成する

文章全体の要点を一文で捉える。
各段落と各文の内容を分ける。
新規作成や追記では、必要な内容を文章として作成する。
改訂では、利用者が求めた変更を反映する。

### 4. 構成を組み直す

要点を詳細より先に置く。
列挙が何を示すかを、個別項目より先に置く。
三項目以上の列挙を、後続の箇条書きへ移す。
話題を見出しで分ける。
並列する情報を箇条書きにする。

### 5. 文を分割する

複数の主要な内容を含む文を分ける。
分割後の論理関係を確認する。

### 6. GFM として整える

見出しとリストの階層を確認する。
入力に含まれる GFM の構文を壊さない。

## 出力

文章の作成または変更だけを依頼された場合は、既定で完成後の文章だけを提示する。
変更理由や差分は、利用者が求めた場合だけ追加する。

実装や調査などに付随して文書ファイルを変更した場合は、その作業で求められる出力形式に従う。
利用者が求めていない場合は、変更した文書の全文を応答へ重複して掲載しない。

補足を追加する場合も、完成後の文章を先に置く。
補足自体にも、この仕様の文章規則を適用する。

完成後の文章全体を、コードブロックで囲まない。
利用者がコピー用のコードブロックを求めた場合は、その指示を優先する。

## 出力前の確認

出力前に、次の条件を確認する。

- 出力形式が GFM である。
- 一文一義になっている。
- 複数の話題が見出しで分かれている。
- 並列する情報が箇条書きになっている。
- 要点が詳細より先にある。
- 三項目以上の列挙では、その列挙が何を示すかが個別項目より先にある。
- 内容を示さない導入文が、列挙の説明として使われていない。
- 見出しや箇条書きを使えない場合は、個別項目や適用範囲が文末の括弧内にある。
- 利用者が求めた内容が作成または変更されている。
- 利用者が変更を求めていない意味と事実関係が保たれている。
- 技術用語が不必要に一般語へ言い換えられていない。
- 利用者の明示的な指示が守られている。

1 つでも満たさない場合は、完了としない。
