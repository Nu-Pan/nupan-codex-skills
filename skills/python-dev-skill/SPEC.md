# Python 開発を支えるスキルの仕様

## 目的と適用場面

プロジェクトの構成に合う方法で Python を実装し、必要な品質を検証する。Python の開発、修正、レビュー、開発環境や性能計測の整備に適用する。ただし、レビューや検査だけの依頼では、依存や設定を自動的に変更しない。

## プロジェクトの環境を使う

設定ファイルと開発手順から、Python のバージョン、依存管理方法、パッケージ構成、品質ゲートを確認し、プロジェクトが宣言する環境を使う。バージョンの指定がなければ Python 3.11 以上を使う。また、依存管理方法がなければリポジトリ内の `.venv` を使う。検査は選択した Python インタープリターから起動し、グローバル環境へ開発依存を追加しない。

既存の検査で何を確かめられるかを調べ、不足する検証に合うツールを選ぶ。例えば、静的検査には Ruff や mypy が候補になる。ツールを導入する場合は、何を検証するために必要かを説明し、プロジェクトの開発依存へ記録する。

## 挙動とパッケージを検証する

対象プロジェクトのテストランナーとテスト構成を使う。pytest では、テストが操作するファイルシステム、環境変数、作業ディレクトリなどを fixture で隔離する。なお、利用が任意とされている外部実行ファイルがない場合は、その理由を明示してテストをスキップできる。

パッケージとして公開するファイルの構成やリソースを変更した場合は、インストール後を想定した配置でも、モジュールをインポートでき、リソースを参照できることを確認する。ソースをチェックアウトした環境で動いても、配布後の配置ではインポートや参照ができない場合があるためである。

処理が停止して完了しないおそれのあるテストには、実行を打ち切れる仕組みを用意する。既存の方法で不足する場合は、例えば pytest-timeout を候補とし、実測した正常時の所要時間と環境によるばらつきから実行時間の上限を選ぶ。ただし、タイムアウトせずに完了したことだけで、性能を確認したことにはしない。

## 静的検査とリソース検査を選ぶ

lint、フォーマット、型の検査は既存の設定に従う。検証時はファイルを書き換えないモードを使い、修正と検査を区別する。その際、型エラーや警告を、広い除外や根拠のない型指定で隠さない。また、新たに検査を導入する場合は、既存コードの状態に合う範囲と厳しさから始める。

リソースの寿命を検証するときは、Python の開発モードを有効にし、`ResourceWarning` をエラーとして扱う方法を使える。既存の品質ゲートでこの検査が定められている場合は、その設定で実行する。ただし、この検査による評価は、検査で観測できるリソースの扱いに限る。

警告を除外する必要があれば、発生元を調べる。そのうえで、第三者に由来すると確認できた警告だけを、理由と範囲を明示して除外する。

## 性能について判断する

性能について判断する必要がある変更では、代表的な処理経路を実測する。計測の必要性は、依頼や性能要件に加え、処理量や待ち時間への影響、性能回帰の兆候から判断する。その際、既存のベンチマークを優先し、変更前後を同じ条件で比較する。

計測手段は、性能の判断に必要な情報を観測できるかで選ぶ。次に、観測する内容に応じた手段の例を示す。

| 観測したいこと | 手段の例 |
| --- | --- |
| 代表的な処理経路の経過時間 | 既存のベンチマーク、`time.perf_counter_ns()` |
| 独立した小さな処理の時間 | `timeit` |
| 実行を分離した反復計測や、結果の継続比較 | `pyperf`、`pytest-benchmark` |
| CPU 時間の内訳 | `cProfile` と `pstats`、`py-spy` |
| メモリの割り当てや使用量 | `tracemalloc`、Memray |

小さな処理を切り出したマイクロベンチマークで分かるのは、切り出した処理の時間である。そのため、利用者の待ち時間を判断するには、起動や I/O を含む経路を測る。また、プロファイラー自体も所要時間に影響するため、原因を調べた後はプロファイラーを使わずに再計測する。計測は許可された権限の範囲で行う。

## 完了時の確認と報告

変更中は関連箇所を検査し、完了前にはプロジェクトが定める品質ゲートとテスト一式を、現在の成果物に対して実行する。ただし、共通の品質ゲートがなければ、変更した挙動と、その挙動を利用する側への影響を確認できる検証範囲を選ぶ。その際、未設定のツール一式を追加することを完了条件にしない。

ほかの規則を併用する場合は、同じ検査や計測を共用する。最後に、実行した検査と結果、検証できなかった範囲を報告する。その際、性能を判断した場合は実測値と条件を、ツールを追加した場合はその必要性を添える。
