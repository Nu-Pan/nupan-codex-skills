# Python 開発を支えるスキルの仕様

## 目的と適用場面

プロジェクトの構成に合う方法で Python を実装し、必要な品質を検証する。
Python の開発、修正、レビュー、開発環境や性能計測の整備に適用する。
ただし、レビューや検査だけの依頼では、依存や設定を自動的に変更しない。

## プロジェクトの環境を使う

設定ファイルと開発手順から、Python のバージョン、依存管理、パッケージ構成、品質ゲートを確認する。
宣言された環境を優先し、バージョンの指定がなければ Python 3.11 以上を使う。
また、依存管理方法がない場合は、リポジトリ内の `.venv` を使う。
検査は選択した interpreter から起動し、グローバル環境へ開発依存を追加しない。

既存の検査で何を確かめられるかを調べ、不足する検証に合うツールを選ぶ。静的検査の候補には、例えば Ruff や mypy がある。導入する理由は作業に必要な観測へ結び付け、プロジェクトの開発依存へ記録する。

## 挙動とパッケージを検証する

対象プロジェクトの runner とテスト構成を使う。
pytest では、テストが触る filesystem、環境変数、作業ディレクトリなどを fixture で隔離する。
なお、optional な外部 executable がない場合は、理由を指定した skip を使える。

パッケージの公開構成や resource を変更した場合は、install 後相当の配置でも import と参照を確認する。
source checkout から動くことだけで、配布後の構成を確認済みとしない。

停止するおそれのあるテストには、打ち切れる仕組みを用意する。
既存の方法で不足する場合は、例えば pytest-timeout を候補とし、実測した正常時間と環境の揺らぎに合う上限を選ぶ。
ただし、timeout の成功は、性能の確認とは区別する。

## 静的検査とリソース検査を選ぶ

lint、format、型検査は既存の設定に従う。
検証時は書き換えなしのモードを使い、修正と検査を区別する。
その際、型エラーや警告を、広い除外や根拠のない型指定で隠さない。
また、新たに検査を導入する場合は、既存コードの状態に合う範囲と厳しさから始める。

リソースの寿命を検証するときは、Python development mode と `ResourceWarning` のエラー化を使える。ただし、既存の品質ゲートならその設定で実行する。警告を除外する必要があれば発生元を調べ、確認した第三者由来の警告に範囲と理由を限定する。結果は、この方法で観測できる範囲の根拠として扱う。

## 性能について判断する

性能について判断する必要がある変更では、代表経路を実測する。必要性は依頼や性能要件と、処理量・待ち時間への影響や回帰の兆候から判断する。既存の benchmark を優先し、同じ条件で比較する。

計測の目的に応じた手段の例を示す。

| 観測したいこと | 手段の例 |
| --- | --- |
| 代表経路の経過時間 | 既存 benchmark、`time.perf_counter_ns()` |
| 独立した小さな処理の時間 | `timeit` |
| 分離した反復や結果の継続比較 | `pyperf`、`pytest-benchmark` |
| CPU 時間の内訳 | `cProfile` と `pstats`、`py-spy` |
| allocation や memory の使用 | `tracemalloc`、Memray |

手段は必要な観測が得られるかで選ぶ。microbenchmark はその処理の時間を示すため、利用者の待ち時間を判断するには起動や I/O を含む経路を測る。また、profiler 自身も所要時間に影響するため、原因を調べた後は profiler なしで再計測する。計測は許可された権限の範囲で行う。

## 完了時の確認と報告

変更中は関連箇所の検査を使い、完了前にはプロジェクトが定める品質ゲートと full test を現在の成果物に対して実行する。
ただし、共通ゲートがなければ、変更した挙動と利用側を検証できる範囲を選ぶ。
未設定のツール一式を追加することを完了条件にしない。

併用する場合は、同じ検査や計測を共用する。
最後に、実行した検査と結果、検証できなかった範囲を報告する。
その際、性能を判断した場合は実測値と条件を、ツールを追加した場合はその必要性を添える。
