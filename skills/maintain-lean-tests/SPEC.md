# maintain-lean-tests の仕様

## 目的

このスキルは、ソフトウェアのテストと fixture を、現行仕様の検証に必要な最小構成に保つ。
実装詳細ではなく、意味のある外部挙動または制御ロジックを検証する。

変更後のテストは、次の状態を満たす。

- 現行仕様上の挙動または制御ロジックを検証している。
- 同じ観点のケースが不要に分散または重複していない。
- 旧仕様や削除済み実装に対応するテストが残っていない。
- fixture が検証対象に対して必要な大きさに収まっている。
- プロジェクトが責任を持たない第三者システムの品質を検証対象にしていない。
- 性能回帰の検査が、実測した根拠と安定した条件に基づいている。

このファイルは、`maintain-lean-tests` のスキル仕様の正本である。
実行時仕様を変更するときは、先にこのファイルを変更する。

## 適用条件

言語やテストフレームワークを問わず、テストと fixture を追加、変更、整理する作業に、このスキルを使用する。
対象となる作業には、次の内容を含む。

- 新しい挙動に対応するテストの追加
- 既存テストへのケース追加
- 重複テストの統合
- 旧仕様または削除済み実装に対応するテストの削除
- fixture、sample、snapshot、test data の縮小
- 実装詳細へ依存するテストの見直し
- 性能回帰 test と benchmark の追加または見直し

## 対象外

次の作業は、このスキルだけの対象にしない。

- テストフレームワーク固有の導入手順や品質ゲートの決定
- 正本仕様またはプロダクトコードの変更
- 手動確認だけで成立する受け入れ作業
- プロジェクトが明示的に品質保証の責任を持つ第三者サービスの評価
- テストを減らすこと自体を目的とする変更

対象リポジトリが言語固有のテストスキルや検査規則を持つ場合は、それらも適用する。

## 入力と前提

必要な入力を次に示す。

- 利用者が要求する挙動
- 対象リポジトリの正本仕様とテスト規則
- 変更対象の実装と外部から観測可能な結果
- 既存のテスト、fixture、sample、snapshot
- 対象リポジトリが定める focused test と full test の実行方法
- 明示された性能要件、既存 benchmark、実測した性能回帰

対象リポジトリのテスト戦略、命名、配置、ツール設定を優先する。
テストの簡潔さを、必要な回帰検出能力より優先しない。

## 実行時の規則

### 意味のある挙動を検証する

- 現行仕様上の外部挙動または意味のある制御ロジックを検証する。
- 内部 helper の呼び出し順、私有識別子、交換可能な内部構造だけを固定するテストを追加しない。
- 実装詳細を使わなくても同じ要求を検証できる場合は、外部から観測可能な結果で検証する。
- プロジェクトが責任を持つ契約と、第三者実装の内部品質を区別する。

### 類似ケースを集約する

- 似たテストを追加する前に、既存テストへケースを追加できないか確認する。
- 同じ観点で入力だけが異なるケースは、対象フレームワークの parametrized test、table-driven test、または同等の仕組みへ集約する。
- 同じ失敗を重複して検出するテストを削除または統合する。
- 同じ観点を不要に複数のテスト関数へ分散させない。
- 集約によって失敗原因が判別しにくくなる場合は、独立したテストを維持する。

### 旧テストを残さない

- 古い仕様に対応するテストを削除する。
- 削除済み実装や置換済み経路に対応するテストを削除する。
- 新しい実装へ移行した場合は、旧実装専用の fixture、定数、helper、snapshot も整理する。
- 互換挙動を現行仕様が要求する場合だけ、その互換テストを残す。
- 互換テストを残す場合は、対象となる契約と削除可能になる条件を読み取れるようにする。

### fixture を必要最小限にする

- fixture、sample、snapshot、test data を、検証対象に必要な最小内容にする。
- 小さな入力で検証できる場合は、実プロジェクト規模の fixture を追加しない。
- 複数のテストで同じ fixture を使う場合は、共有によって各テストの前提が不明確にならない範囲で集約する。
- 検証対象より大きく、無関係な失敗原因を増やす fixture を作らない。

### 責任範囲を越えた品質を検証しない

- 外部 CLI、外部サービス、モデル、provider、ライブラリ自体の品質を、対象プロジェクトのテストで保証しない。
- 対象プロジェクトが責任を持つ連携、入力変換、出力処理、エラー処理は検証する。
- 第三者システムの意味的な出力品質を検証する必要がある場合は、その責任が正本仕様に明示されていることを確認する。

### 性能回帰の検査を実測に基づける

- 性能 test または benchmark を、定量的な性能要件または安定して再現できる性能回帰がある場合だけ追加する。
- 代表的な入力を同じ条件で反復計測し、観測した実行時間とばらつきを記録する。
- wall-clock time の assertion には、観測したばらつきより十分に大きい余裕を持たせる。
- 共有 CI で安定しない厳密な時間 assertion を、通常の機能 test へ追加しない。
- timeout を停止検出として扱い、処理速度の合格を示す性能 test として扱わない。
- 安定した自動判定ができない場合は、flaky な test を追加せず、再現用 benchmark と実測結果を報告する。

### テストコード自体を簡潔に保つ

- 未使用の import、定数、helper、fixture、sample を残さない。
- 同じ責務を持つ test helper を複数の名前や場所で重複させない。
- 既存 helper の修正または再利用で足りる場合は、新しい helper を追加しない。
- 新しい抽象化は、実在する重複を減らす場合または明確な責務境界を示す場合だけ追加する。
- コードから明らかな処理手順をコメントや docstring で繰り返さない。
- テストだけから読み取りにくい意図、制約、失敗条件は、必要な範囲でコメントに残す。
- 現行仕様の理解に寄与しない TODO、NOTE、古い仕様のコメントを残さない。

### テストファイルを意味上のまとまりに保つ

- ファイルの分割と統合を、検証責務、凝集性、同時に読む必要がある文脈に基づいて判断する。
- 独立した複数の検証責務を持つファイルは、責務境界に沿って分割する。
- 同じ検証責務で常に一緒に読まれる小さなファイルは、統合を検討する。
- 1 ファイルが 8,000 文字を超える場合は、自然な分割点がないか確認する。
- 1 ファイルが 16,000 文字を超える場合は、分割しない理由を責務、凝集性、読解文脈から説明できる状態にする。
- 文字数だけを根拠に、強く結合したテストを不自然に分割しない。

対象リポジトリが別の基準を定める場合は、その基準を優先する。

### テストを変更する

1. 検証すべき正本仕様上の挙動または制御ロジックを特定する。
2. 同じ観点を検証する既存テストを探す。
3. 既存テストへのケース追加、既存テストの修正、新規テストの順で実現方法を選ぶ。
4. 旧仕様、削除済み実装、重複観点に対応するテストと fixture を整理する。
5. 未使用要素、重複 helper、不要なコメント、ファイルの責務を整理する。
6. focused test を実行し、変更中の失敗を解消する。
7. 対象リポジトリが定める full test と関連する品質ゲートを fresh に実行する。
8. テスト差分全体を見直し、過大な fixture、重複、不要物を整理する。

## 出力

テスト変更を依頼された場合は、対象リポジトリへ変更を反映する。
レビューだけを依頼された場合は、ファイルを変更しない。

最終報告では、次の内容を簡潔に示す。

- 追加、変更、削除、統合したテスト観点
- 整理した fixture や旧テスト
- 実行した focused test、full test、品質ゲートと結果
- 性能 test を変更した場合は、計測条件、実測値、閾値の根拠
- 未実行または失敗した検査がある場合は、その理由

## 検証

完了前に、次の条件を確認する。

- 各テストが、現行仕様上の挙動または意味のある制御ロジックへ対応している。
- 実装詳細だけを固定するテストが追加されていない。
- 既存テストへ追加できるケースが、理由なく新しいテストへ分散していない。
- 同じ観点や失敗を重複して検出するテストがない。
- 旧仕様または削除済み実装に対応するテストが残っていない。
- fixture が検証対象に必要な大きさに収まっている。
- 第三者システムの品質を、正本仕様上の責任なしに保証していない。
- 性能 test と閾値が、実測値と観測したばらつきに基づいている。
- timeout の成功だけを、処理速度の根拠にしていない。
- 不安定な時間 assertion を、通常の機能 test へ追加していない。
- 未使用の import、定数、helper、fixture、sample が残っていない。
- コメントと docstring が、コードから読み取りにくい意図や制約だけを補っている。
- テストファイルの責務と大きさが、対象リポジトリの基準に適合している。
- focused test と full test が、対象リポジトリの規則に従って実行されている。

1 つでも満たさない場合は、完了としない。

## 重視する価値

テストも読み取り、保守、更新が必要な実装成果物として扱う。
回帰検出能力を保ったまま、仕様変更時に修正すべきテストの量を抑える。
