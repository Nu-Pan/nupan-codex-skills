# Codex CLI 挙動を検証するスキルの仕様

## 目的と適用場面

Codex CLI に依存するアプリの設計や制御、互換性を、対象版のソースと安全な実測に基づいて判断する。CLI を直接、または SDK やラッパーを介してローカルプロセスとして使うアプリの設計、実装、変更、レビューに適用する。ただし、CLI を開発道具として使うだけの作業や、ローカル CLI を起動しない API 統合には適用しない。配布設定では暗黙の適用を有効にする。

## 依存する挙動と対象版を確かめる

検証の対象は、アプリの設計や制御、互換性の判断を左右する CLI の挙動とする。アプリの要求と CLI との連携コードを読み、アプリが依存する挙動を特定する。そのうえで、入出力や終了処理など、その挙動を確かめるために必要な範囲を調べる。

調査するソースは、アプリが宣言するコミット、または固定されたバージョンを優先して選ぶ。特定できなければ、アプリが実際に起動する CLI の版を確認する。バージョンが範囲でしか指定されていない場合は、ロックファイルや実行環境から具体的な版を調べる。バージョンを基に調査する場合は、対応する `openai/codex` のリリースタグ `rust-v{{version}}` が指すコミットを特定する。

タグを根拠にする場合は、タグが指すコミットオブジェクトの SHA を取得する。注釈付きタグにはタグ自体の SHA もあるため、`^{commit}` またはリモートの peeled reference を使ってコミットの SHA を確かめる。

それでも対象を特定できない場合は、最新の安定版を調査用に代用する。その際、代用した理由と、対象環境の挙動は未確認であることを示す。なお、プレリリース版は、利用者やアプリが対象として指定した場合に使う。

## 実際に動作するコードで根拠を確かめる

重要な挙動は、対象リビジョンの `openai/codex` で、製品として実際に動作するコードを読んで確認する。その際、判断に必要な呼び出し元と実装先をたどり、対象コミットに根拠となるファイルと行が存在することを確かめる。その根拠を参照できるように、次の形式でコミットを固定した恒久リンクを使う。

```text
https://github.com/openai/codex/blob/{{commit-sha}}/{{source-path}}#L{{start-line}}-L{{end-line}}
```

`{{commit-sha}}` は省略しない40桁のコミット SHA とし、リンクの行範囲は判断を支える箇所に絞る。公式文書やテストは解釈の補強に使えるが、実際に動作するコードの確認を置き換えない。

一方、対象アプリが満たすべき要求は、アプリの正本仕様と利用者の指示から確認する。CLI の実装を理由に、それらの要求を書き換えない。また、現在の内部実装を確認できても、将来の互換性や公開契約を保証する根拠にはしない。

ソースから読み取った挙動が、文書の説明や実測した挙動と異なる場合は、調査したソースのリビジョンと、文書や実測の対象版・条件を照合する。それでも不一致が残る場合は、ソース、文書、実測のそれぞれから確認した事実を分けて示し、実際の挙動を断定しない。なお、非公開のサーバー側処理については、CLI 側で確認できる範囲までを根拠として扱う。

## 実測と互換性を確認する

安全に実行できる場合は、ソースの確認で前提にしたバージョン、プラットフォーム、設定にそろえて CLI を実行し、重要な挙動に絞って観測する。その際、実行条件の違いを確かめられる方法を選び、一時的な作業ディレクトリと非機密の入力を使う。認証や外部への作用が必要な操作は、既存の権限とリポジトリの規則に従う。

一方、実測できない場合は、その理由と判断への影響を示す。いずれの場合も、ソースから確認した内容と実測した内容を区別する。

アプリが依存する重要な挙動については、ソースで確認した内容に基づき、互換性を保つ対策を評価する。実装・変更を任されている場合は必要な対策を設け、検証や根拠の記録だけの依頼では、確認できた対策と不足を報告する。例えば、対応バージョンの固定、起動時のバージョン確認、フォールバックなどがある。また、一つの互換性対策でアプリが依存する複数の挙動を扱える場合は、その対策を共用する。

フォールバックは、必要な機能が使えない場合に安全な動作へ切り替える対策である。採用する場合は、処理が失敗する条件と利用者への通知内容を明らかにする。

## 根拠を残して報告する

根拠を示す際は、アプリがその挙動に依存する理由と、ソースの確認や実測で分かったことを説明する。そのうえで、調査したソースのリビジョンと実測時の条件を示し、ソースの確認と実測が同じ条件に基づくかを読み手が確かめられるようにする。また、確認方法と残る不確実性を明らかにする。

根拠を成果物へ残す依頼では、詳細を既存の設計文書など一箇所へ集約し、CLI との連携コードの必要な箇所から参照する。その際、文書を新設する場合もリポジトリの配置に合わせる。

検証で、アプリが想定する挙動と CLI の挙動に不一致が見つかった場合は、元の依頼とセッションで認められた作業範囲から、修正の可否と範囲を判断する。アプリの実装・変更を任されている場合は、その作業に必要な不整合の解消も含める。最終報告では、不一致の根拠と影響、対応内容、検証結果を伝え、詳細を残した場所を案内する。一方、参照先がなければ、報告自体に、実際に動作するコードへの恒久リンクと必要な根拠を載せる。

レビューだけの依頼ではファイルを変更しない。レビューでは、挙動の根拠を参照でき、互換性対策を確認できるかを確かめる。その際、記載場所の好みを挙動上の不整合とみなさない。アプリが依存する重要な挙動について、根拠や互換性対策を確認できない場合や、挙動自体が未確認の場合は、理由と判断への影響を報告する。

## 評価

重要な挙動ごとに、対象版のソースによる根拠をたどれるか、ソースの確認と実測を区別できるか、互換性対策を追えるかを確認する。その際、同じ調査や検証は共用する。ただし、実際に動作するコードを確認できない重要な挙動が残る場合は、検証完了としない。
