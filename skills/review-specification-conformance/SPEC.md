# 仕様と実装の適合性をレビューするスキルの仕様

## 目的と適用場面

人間が判断すべき問題を、確認済みの根拠に基づいて報告する。正本仕様の整合性・実現可能性・表記と、仕様に対する実装の適合性をレビューする作業に適用する。修正を依頼された場合は、所見を解消して再検証する。

## 判断の根拠を集める

依頼からレビューの対象と修正の権限を確認し、リポジトリが指定する正本と、その優先関係を調べる。そのうえで、指定ファイルや最近の差分を入口に、判断に必要な関連仕様、実装、テストをたどる。また、既知の所見も現在の成果物に照らして確かめる。

要求の根拠には正本仕様を使う。改訂のレビューでは、利用者の変更要求と改訂前の仕様をよりどころに、必要な要求が残っているか、追加された制約に根拠があるかを確かめる。一方、実装の調査や領域固有の検査から分かったことは、観測した事実として扱う。その事実を要求と照合し、不一致を確認してから所見にする。

## 必要な判断を妨げる問題を見つける

要求が満たされているか、成果物からその根拠を読み取れるかを確かめる。仕様の不足を指摘するときは、既存の原則ではどの重要な判断に困るかを示す。ただし、目的を満たす複数の解釈や実装が可能であることは、仕様の欠陥ではない。

仕様単体では、次の重大度で問題を報告する。

| 重大度 | 判定と示す根拠 |
| --- | --- |
| fatal | 明確な矛盾、または仕様に従う実装者の裁量では解消できない問題。両立しない要求や実現できない結果を具体的に示す。 |
| minor | 意味や検索性を損なう、誤字や用語不統一などの表記上の問題。意味を保った修正として説明する。 |

一方、改訂案や実装の適合性をレビューする場合は、要求を満たす実現方法の違いと、要求に反する挙動を区別する。そのうえで、根拠となる要求と成果物の不一致を示し、問題の種類に合う説明を選ぶ。また、仕様の意図から著しく外れた実装も、根拠を示せる場合は所見にする。実装単体の明らかな致命的バグや、現行の仕様と実装のいずれにも必要のない旧仕様の名残も扱える。

所見では、関係する要求と成果物の問題を示し、その問題が読み手の判断に与える影響を説明する。その際、根拠となる箇所を示し、特定できない場合は理由を添える。また、原因と解決方法が同じ所見はまとめ、所見どうしに矛盾があれば解消する。一般的な品質向上や表現の好みは、このレビューの所見に含めない。

## 依頼された修正を行う

レビューだけの依頼ではファイルを変更しない。一方、改訂も依頼された場合は、依頼された変更を反映してから成果物をレビューする。また、所見の修正を依頼された場合は、確認した問題の解消に必要な関連箇所を一体として組み直す。

変更は、利用者の依頼または確認した所見を根拠として行い、影響範囲外の意味を保つ。例外を足す前に主文や責務の分け方を見直し、修正後に再レビューとリポジトリで定められた検証を行う。その際、同じ調査や検査は併用するスキルと共用する。なお、Git のステージング、コミット、プッシュは、それぞれを依頼された場合に行う。

## 結果を報告する

現在の成果物で確認した問題を報告する。既知の所見には再検証した結果を示し、未確認の候補は未確認であることを明記する。また、修正済みの問題には、対応内容と検証結果を添える。

仕様単体の問題は fatal、minor の順に示し、適合性レビューの所見は問題の種類が分かる形にする。新規所見がなければ、その旨を示す。

レビューの妥当性は、具体的な根拠と判断への影響で評価する。仕様の網羅性や指摘件数を増やすことを目的にしない。
