# 仕様と実装の適合性をレビューするスキルの仕様

## 目的と適用場面

人間が判断すべき問題を、確認済みの根拠に基づいて報告する。
正本仕様の整合性・実現可能性・表記と、仕様に対する実装の適合性をレビューする作業に適用する。
修正を依頼された場合は、所見を解消して再検証する。
一般的な品質向上や好みだけに基づく提案は、このレビューの目的に含めない。

## 根拠を集める

依頼からレビューの対象と修正権限を確認する。
リポジトリが指定する正本と優先関係を調べ、判断に必要な関連仕様、実装、テストを読む。
指定された一ファイルや、推測した最近の差分だけで調査範囲を狭めない。
既知の所見があれば、現在も成立するかを確認する。

正本仕様を要求の根拠とし、実装から要求を逆算しない。
領域固有の検査は観測の根拠として利用する。
検査が失敗したことだけで、正本仕様上の不整合と断定しない。

## 必要な判断を妨げる問題を見つける

仕様単体のレビューでは、次の重大度を使う。

| 重大度 | 判定基準 |
| --- | --- |
| fatal | 仕様の明確な矛盾、または仕様に従う実装者の裁量では解消できない問題。 |
| minor | 意味や検索性を損なう、誤字や用語不統一などの表記上の問題。 |

fatal 所見は、両立しない要求や実現できない結果を具体的に示す。
minor 所見は、意味を保った表記の修正として説明できるものにする。

仕様と実装の適合性では、要求と観測した挙動の不一致を示す。
明示された要求だけでなく、仕様から読み取れる意図と著しく乖離する実装も、その根拠を示せる場合は所見とする。
実装単体で明らかな致命的バグや、現行仕様にも実装にも必要性のない旧仕様の残骸も対象にできる。
このレビューへ fatal・minor の分類を強制しない。

文脈と原則から必要な判断ができる場合は、個別ケースの明記がないことを問題にしない。
複数の妥当な実装や解釈が残ることは、矛盾ではない。
候補を所見にする前に、どの必要な判断が妨げられ、原則に沿った判断ではなぜ解消できないのかを確かめる。

## 所見をまとめる

所見には、問題の要点、根拠となるファイルと位置、必要な判断への影響を示す。
要求と観測を区別し、確認できた内容から問題を説明する。
位置を特定できない場合は、その理由を示し、行番号を推測しない。
同じ原因と解決を持つ所見はまとめ、相互矛盾を解消する。

## 修正し、再検証する

レビューだけの依頼ではファイルを変更しない。
依頼された改訂がある場合は、その要求を実現し、改訂後の成果物をレビューする。
所見の修正を求められた場合は、確認した問題の解消に必要な関連箇所を一体として組み直す。
変更の根拠を依頼または所見へ結び付け、影響範囲外の意味を保つ。
例外を足す前に、主文や責務の分け方を見直す。

修正後の成果物を再レビューし、リポジトリが定める検証を実行する。
他のスキルを併用する場合は、同じ調査や検査を共用する。
Git の stage、commit、push は、それを依頼された場合に行う。

## 結果の評価と報告

報告時に再検証して残っている問題と、修正済みの対応結果を区別する。
既知の所見を新規所見として重複報告しない。
仕様単体では fatal、minor の順に示し、適合性レビューでは問題の種類が分かる形にする。
新規所見がない場合はその旨を簡潔に示す。
修正した場合は対応と検証結果を添える。

所見の妥当性は、具体的な根拠と判断への影響で評価する。
仕様の網羅性を高めるためだけの指摘や、表現の好みを混ぜない。
未確認の候補は確定した所見として報告しない。
