# 仕様と実装の適合性をレビューするスキルの仕様

## 目的と適用場面

人間が判断すべき問題を、確認済みの根拠に基づいて報告する。正本仕様の整合性・実現可能性・表記と、仕様に対する実装の適合性をレビューする作業に適用する。修正を依頼された場合は、所見を解消して再検証する。

## 判断の根拠を集める

依頼から対象と修正権限を確認し、リポジトリが指定する正本と優先関係を調べる。必要な関連仕様、実装、テストをたどり、問題を判断できる範囲を読む。指定ファイルや最近の差分は調査の入口とし、既知の所見も現在の成果物で確かめる。

要求の根拠には正本仕様を使う。改訂のレビューでは、利用者の変更要求と改訂前の仕様をよりどころに、必要な要求が残り、追加した制約に根拠があるかを確かめる。実装や領域固有の検査結果は観測として扱い、どの要求との不一致かを確かめて所見にする。

## 必要な判断を妨げる問題を見つける

候補を所見にする前に、どの必要な判断が妨げられ、原則と文脈に沿った判断ではなぜ解消できないかを確かめる。目的を満たす複数の解釈や実装が残ることは、矛盾ではない。個別ケースの明記がなくても原則から判断できるなら、追記を求めない。

仕様単体では、次の重大度で問題を報告する。

| 重大度 | 判定と示す根拠 |
| --- | --- |
| fatal | 明確な矛盾、または仕様に従う実装者の裁量では解消できない問題。両立しない要求や実現できない結果を具体的に示す。 |
| minor | 意味や検索性を損なう、誤字や用語不統一などの表記上の問題。意味を保った修正として説明する。 |

改訂案や実装の適合性では、根拠となる要求と成果物の不一致を示す。仕様の意図から著しく乖離する実装も、根拠を示せる場合は所見にする。実装単体の明らかな致命的バグや、現行仕様にも実装にも必要性のない旧仕様の残骸も扱える。このレビューでは、問題の種類に合う説明を選ぶ。

所見は、どの要求に対して何が問題となり、判断にどう影響するかを、根拠の位置へたどれる形で説明する。位置を特定できない場合は理由を添える。同じ原因と解決を持つ所見をまとめ、相互矛盾を解消する。一般的な品質向上や表現の好みは、このレビューの所見に含めない。

## 依頼された修正を行う

レビューだけの依頼ではファイルを変更しない。改訂も依頼された場合は、その要求を実現した成果物をレビューする。所見の修正では、確認した問題の解消に必要な関連箇所を一体として組み直す。

変更を依頼または所見へ結び付け、影響範囲外の意味を保つ。例外を足す前に主文や責務の分け方を見直し、修正後に再レビューとリポジトリの検証を行う。同じ調査や検査は併用するスキルと共用する。Git の stage・commit・push は、それを依頼された場合に行う。

## 結果を報告する

現在の成果物で確認した問題を報告する。既知の所見は再検証した状態を示し、未確認の候補と修正済みの対応結果はその状態が分かるように伝える。仕様単体では fatal、minor の順に示し、適合性レビューでは問題の種類が分かる形にする。新規所見がなければその旨を示し、修正した場合は対応と検証結果を添える。

レビューの妥当性は、具体的な根拠と判断への影響で評価する。仕様の網羅性や指摘件数を増やすことを目的にしない。
