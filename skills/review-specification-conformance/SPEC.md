# 仕様と実装の適合性をレビューするスキルの仕様

## 目的と適用場面

人間の判断に必要な所見を、確認済みの根拠に基づいて整理する。正本仕様の整合性・実現可能性・表記と、仕様に対する実装の適合性をレビューする作業に適用する。責務は、要求と成果物を照合して問題を判定することである。所見の用途や対応は、利用者の指示と依頼文脈に委ねる。レビューだけの依頼では成果物を変更せず、修正も任されている場合は、確認した問題を対象とする編集・実装・テストの保守へつなげる。

## 判断の根拠を集める

依頼からレビューの対象を確認し、リポジトリが指定する正本と、その優先関係を調べる。そのうえで、指定ファイルや最近の差分から、判断に必要な関連仕様、実装、テストをたどる。

要求の根拠には正本仕様を使う。改訂案をレビューする場合は、利用者の変更要求と改訂前の仕様に照らし、必要な要求の保持と、条件や義務を変更する根拠を確かめる。改訂後の規定を両立させる実装があっても、それだけでは要求の変更を正当化できない。変更要求に反する条件の変更や、根拠のない義務の追加は、改訂案の適合性の問題として扱う。一方、実装の調査や領域固有の検査から分かったことは、観測した事実として扱う。その事実を要求と照合し、不一致を確認してから所見にする。既に同じ対象・条件で行った調査や検査は共用し、専門的な検査の成功だけで成果物全体が要求を満たすとは判断しない。

## 必要な判断を妨げる問題を見つける

要求が満たされているか、成果物からその根拠を読み取れるかを確かめる。仕様の不足を指摘するときは、既存の原則ではどの重要な判断に困るかを示す。ただし、目的を満たす複数の解釈や実装が可能であることは、仕様の欠陥ではない。

仕様単体の問題は、次の重大度で分類する。

| 重大度 | 判定と示す根拠 |
| --- | --- |
| fatal | 明確な矛盾、または仕様に従う実装者の裁量では解消できない問題。両立しない要求や実現できない結果を具体的に示す。 |
| minor | 意味や検索性を損なう、誤字や用語不統一などの表記上の問題。意味を保った修正として説明する。 |

一方、改訂案や実装の適合性をレビューする場合は、要求を満たす実現方法の違いと、要求に反する結果を区別する。そのうえで、成果物のどこが根拠となる要求と一致しないかを示し、問題の種類に合う説明を選ぶ。また、仕様の意図から著しく外れた実装も、根拠を示せる場合は所見にする。実装単体の明らかな致命的バグや、現行の仕様と実装のいずれにも必要のない旧仕様の名残も扱える。

一般的な品質向上の提案や表現の好みは、このレビューの所見に含めない。

## 所見を整理する

所見には、問題に関係する要求と、成果物で確認した問題、その種類を示し、読み手の判断にどのような影響があるかを説明する。その際、根拠となる箇所を示し、その箇所を特定できない場合は理由を添える。また、原因と解決方法が同じ所見はまとめ、所見どうしに矛盾があれば解消する。

確認した問題と未確認の候補を区別する。既知の所見は現在の成果物で再検証し、未解決の問題と修正済みの問題を分ける。その際、修正済みの問題には対応内容と検証結果を結び付け、現在の状態を判断できるようにする。

レビューの妥当性は、具体的な根拠と判断への影響で評価する。仕様の網羅性や指摘件数を増やすことを目的にしない。

## 所見の扱い

所見を報告や修正などにどう使うかは、利用者の指示と依頼文脈から判断する。対応範囲や出力方法もその指示に従い、指定されていない部分にだけスキルの既定の扱いを適用する。

報告が求められ、報告する所見の範囲に指定がない場合は、現在の成果物で確認した未解決の問題のうち、仕様単体の問題は fatal のみ、改訂案や実装の適合性レビューの問題は重大度で絞らず報告する。報告対象がなければ、その範囲で該当する所見がないことを示す。一方、minor を含む報告などの指定があれば、それに従う。

この既定の報告範囲は、調査や所見の整理、修正の対象を制限するものではない。
