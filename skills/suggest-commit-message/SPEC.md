# コミットメッセージを提案するスキルの仕様

## 目的と適用場面

セッションで確認した変更の目的と、その過程での判断を根拠に、未コミットの変更全体の主題を伝えるコミットメッセージを提案する。後から履歴を読む人が、差分を開く前に何の変更かを理解できることを重視する。

利用者が `$suggest-commit-message` を明示した場合だけ適用する。そのため、配布設定では暗黙の適用を無効にする。なお、スキル名だけの呼び出しも提案依頼として扱う。

## 変更の意味を確かめる

提案の対象範囲は利用者の追加指示に従い、指定がなければ未コミットの変更全体を対象にする。この範囲には、ステージ済みの変更、未ステージの変更、Git の無視対象ではない未追跡ファイルを含める。

まず対象の Git リポジトリと変更の有無を確認し、対象となる変更がなければ、提案できない理由を簡潔に示す。確認と提案を通じて、Git の状態とファイルは変更しない。

セッションで示された目的や判断、確認済みの作業結果と Git の差分を照合し、変更の意図が現在の変更にどう表れているかを確かめる。セッションで確認できない人間の意図を、差分やリポジトリ内の説明から補わない。

## 主題を一行で表す

セッションで確認できた目的や結果から、変更全体の主題を一行で表す。ファイルや修正項目の列挙だけで主題を伝えようとせず、根拠のない効果や理由も加えない。

例えば、新しいスキルを追加した変更について、次のようにファイル名だけを列挙すると、履歴の読み手には何をするスキルかが分からない。

> SPEC.md、SKILL.md、README.md を追加

追加したスキルの目的が「セッションの意図をコミットメッセージへ反映すること」だとセッションで確認できていれば、次のように表せる。これなら、差分を開く前に何をする機能を追加したかが伝わる。

> セッションの意図を伝えるコミットメッセージ提案スキルを追加

## 出力と評価

指定がなければ、日本語で一行の案を一つ作り、言語指定のないコードブロックで提示する。Conventional Commits の type・scope やコミットメッセージの本文は、求められた場合に付ける。一方、提案できない場合は理由を示し、暫定案は付けない。

他の文章規則を併用する場合も、指定された専用形式を保つ。

評価では、セッションの意図と現在の変更全体が対応し、その主題を読み取れるかを確認する。また、変更についての事実が保たれ、Git の状態やファイルを変更せずに提案できているかを確かめる。
