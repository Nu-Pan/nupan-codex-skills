# suggest-commit-message の仕様

## 目的

このスキルは、そのセッションで扱った目的と判断を根拠に、未コミット変更全体のコミットメッセージを提案する。
差分を読まなくても「一体何の話なのか」が分かる高レベルな意味を、一つのメッセージで伝える。

提案後のコミットメッセージは、次の状態を満たす。

- 利用者が実現しようとした目的または変更の意味が分かる。
- セッションで確認した意図、判断、理由、結果だけに基づいている。
- 未コミット変更全体を一つの意味として表している。
- 差分から直接読み取れる修正項目を列挙していない。
- 既定では、日本語の一行を一案だけ提示している。

このファイルは、`suggest-commit-message` のスキル仕様の正本である。
実行時仕様を変更するときは、先にこのファイルを変更する。

## 適用条件

利用者が `$suggest-commit-message` を明示的に呼び出した場合だけ、このスキルを使用する。
スキル名を含まないコミットメッセージの依頼には、このスキルを暗黙に使用しない。

入力が `$suggest-commit-message` だけの場合は、追加指示なしでコミットメッセージの提案を依頼されたと解釈する。
同じ入力に自然言語の指示が添えられている場合は、その指示も適用する。

明示的な呼び出しだけを許可するため、配布物は次の条件を満たす。

- `SKILL.md` の description に、`$suggest-commit-message` の明示時だけ使用することを記載する。
- `SKILL.md` の description に、暗黙に使用しないことを記載する。
- `agents/openai.yaml` の `policy.allow_implicit_invocation` を `false` にする。

## 対象外

このスキルでは、次の作業を行わない。

- Git の変更を stage または commit する。
- ファイルを作成、変更、削除する。
- 修正したファイル、関数、設定、テストをコミットメッセージとして列挙する。
- Git 差分を言い換えただけの説明を提案する。
- セッションにない高レベルな意味を、差分だけから推測して補う。
- Git リポジトリまたは未コミット変更を確認できない状態でメッセージを作る。

複数の無関係な変更を分割して commit する作業は、このスキルの対象外とする。
一つのメッセージへまとめる意味を確認できない場合は、対象または意図を利用者へ確認する。

## 入力と優先順位

入力として扱う情報を次に示す。

- `$suggest-commit-message` に添えられた利用者の追加指示
- そのセッションで利用者が示した目的、判断、理由、制約
- そのセッションで確認できた作業結果と検証結果
- Git の staged、unstaged、未追跡を含む non-ignored の未コミット変更

判断には、次の優先順位を適用する。

1. 呼び出しに添えられた利用者の明示的な指示に従う。
2. セッションで利用者が示した目的、判断、理由を意味の根拠にする。
3. セッションで確認できた作業結果を、意味と事実の根拠にする。
4. Git の未コミット変更を、対象範囲と事実の確認に使う。

Git 差分は、セッション文脈から得た意味が実際の変更と一致するかを確かめるために使う。
Git 差分を、欠けている目的や理由を補う根拠として使わない。
README、コメント、識別子、Git 履歴に書かれた説明も、セッション文脈の代わりに使わない。

`$suggest-commit-message` だけの入力は、提案の依頼を示す。
この入力自体は、変更の目的、判断、理由、結果を示す意味論的な文脈には数えない。

呼び出しに追加指示がない場合は、staged の有無を問わず未コミット変更全体を一つの対象にする。
ignored の変更と、現在の worktree に含まれないセッション上の話題は対象に含めない。

## 独立性と合成

このスキルは、他のスキルがなくても、セッション文脈と Git の未コミット変更を確認して提案を完成させる。
文章、Git、実装、テストに固有の別スキルを必須条件にしない。

日本語の文章規則が同時に適用される場合は、意味と事実を保つ規則をコミットメッセージにも適用する。
このスキルが定める一行一案の専用形式は維持する。

実装、テスト、仕様、レビューに関する別の作業規則が同時に適用される場合も、このスキルはコミットメッセージの提案だけを担う。
同じセッション調査と Git 状態の確認は一回に統合する。

## 実行時の規則

### 依頼を解釈する

- `$suggest-commit-message` だけが入力された場合は、既定条件で提案する。
- 追加指示がある場合は、指定された言語、件数、形式、対象範囲を既定条件より優先する。
- 追加指示がない場合は、日本語の一行を一案だけ提案する。
- 追加指示がない場合は、Conventional Commits の type、scope、本文を付けない。

### Git の状態を確認する

1. 現在位置が Git リポジトリ内であることを確認する。
2. staged、unstaged、未追跡を含む non-ignored の未コミット変更を確認する。
3. Git の状態を変更する command または option を使用しない。

Git リポジトリでない場合、または未コミット変更がない場合は、コミット対象を確認できないため提案できないことを簡潔に報告する。
この場合は、コミットメッセージをコードブロックで提示しない。

### 意味論的なセッション文脈を確認する

Git 差分を読む前に、次のいずれかが現在のセッションに明示されていることを確認する。

- 利用者が実現しようとした目的
- 変更の方向を決めた判断、理由、制約
- そのセッションで依頼され、確認できた作業結果

呼び出しに添えられた自然言語の指示と、呼び出しより前の会話を確認対象にする。
`$suggest-commit-message` だけの入力は、意味論的なセッション文脈として扱わない。

意味論的なセッション文脈がない場合は、Git 差分を読んで目的を補わない。
変更で実現しようとした目的を、一つの簡潔な質問で確認する。
回答を得るまでは、コミットメッセージを提示しない。

意味論的なセッション文脈がある場合だけ、変更内容を必要な分だけ読む。
変更内容は、対象範囲とセッション文脈との一致を判断するために使う。

### 高レベルな意味を特定する

1. セッションで利用者が実現しようとした目的を特定する。
2. 変更の方向を決めた判断、理由、制約を特定する。
3. 未コミット変更として実現した結果を特定する。
4. 変更全体を一つの話題として表す最小の意味を作る。
5. その意味が未コミット変更全体と一致することを確認する。

「何を変更したか」の一覧ではなく、「一体何の話なのか」へ答える。
高レベルな主題を識別するために必要な名称だけを残す。

差分の列挙に留まる例を次に示す。

> SPEC.md、SKILL.md、README.md を追加

高レベルな意味を示す例を次に示す。

> セッションの意図を伝えるコミットメッセージ提案スキルを追加

### 根拠不足を扱う

次のいずれかに該当する場合は、推測でメッセージを作らない。

- セッション文脈から変更の目的または意味を特定できない。
- 裸の呼び出し以外に、意味論的なセッション文脈がない。
- セッション文脈と未コミット変更が食い違う。
- 未コミット変更が複数の無関係な話題に分かれている。
- 未コミット変更全体を一つにまとめる意図を確認できない。

不足している対象または意図を、一つの簡潔な質問で確認する。
回答を得るまでは、暫定的なコミットメッセージを提示しない。

### メッセージを作る

- セッションで確認した目的、判断、理由、結果だけを使う。
- 未コミット変更全体を一つの意味として表す。
- 変更の目的または利用者にとっての結果を、短い一行で示す。
- 修正項目を読点、接続詞、括弧で列挙しない。
- 差分から直接読み取れる内容を、説明として繰り返さない。
- 根拠のない理由、効果、互換性、品質上の主張を加えない。

## 出力

追加指示がない場合は、完成した日本語のコミットメッセージ一案だけを、言語指定のないコードブロックで提示する。
コードブロックの中には一行だけを置く。
見出し、候補番号、説明、根拠、本文を追加しない。

利用者が別の言語、件数、形式、対象範囲を明示した場合は、その指示に従う。
高レベルな意味をセッション文脈に基づける規則と、未確認の事実を追加しない規則は維持する。

確認が必要な場合は、質問だけを提示する。
提案不能の場合は、理由だけを簡潔に提示する。

## 検証

完了前に、次の条件を確認する。

- `$suggest-commit-message` が明示的に呼び出されている。
- 暗黙起動を許可する設定または説明がない。
- 指定された対象範囲の未コミット変更を確認している。
- セッションの目的、判断、理由、結果が意味の根拠になっている。
- 裸の呼び出しまたは Git の内容を、欠けた意味論的なセッション文脈の代わりにしていない。
- 未コミット変更全体について「一体何の話なのか」が分かる。
- 修正内容またはファイルを列挙していない。
- Git 差分を読めば分かることを説明として繰り返していない。
- セッションと Git で確認できない事実を追加していない。
- 追加指示がない場合は、日本語の一行一案だけをコードブロックで提示している。
- Git の状態とファイルを変更していない。

一つでも満たさない場合は、修正するか、必要な情報を利用者へ確認してから完了する。

## 重視する価値

Git 差分は、変更がどのように実装されたかを示せる。
一方で、変更の目的、判断、理由は差分だけでは失われやすい。

コミットメッセージは、後から履歴を読む人が変更の主題を見つけるための入口として扱う。
実装項目の再掲より、セッションに現れた人間の意図を短く残すことを重視する。
