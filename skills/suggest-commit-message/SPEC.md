# コミットメッセージを提案するスキルの仕様

## 目的と適用場面

セッションで扱った目的と判断を根拠に、未コミットの変更全体の主題を伝えるコミットメッセージを提案する。後から履歴を読む人が、差分を開く前に何の変更かを理解できることを重視する。

利用者が `$suggest-commit-message` を明示した場合だけ適用する。そのため、配布設定では暗黙の適用を無効にする。なお、スキル名だけの呼び出しも提案依頼として扱う。

## 変更の意味を確かめる

利用者の追加指示を優先し、指定がなければ未コミットの変更全体を対象にする。まず対象の Git リポジトリと変更の有無を確認する。対象には、Git の無視対象を除く、ステージ済み、未ステージ、未追跡の変更を含める。対象となる変更がなければ、提案できない理由を簡潔に示す。なお、Git の状態とファイルは変更しない。

差分を読む前に、セッションで示された目的や判断、確認済みの作業結果から、変更の意図を確かめる。目的が分からなければ、一つの簡潔な質問で確認してから差分を読む。

そのうえで、Git の差分を読み、確認した意図と現在の変更を照合する。意図が変更にどう表れているかを判断できなければ、不足する文脈を確認する。セッションで確認できない人間の意図を、差分やリポジトリ内の説明から補わない。

## 主題を一行で表す

セッションで確認できた目的や結果を、変更全体に通じる言葉で表す。ファイルや修正項目の列挙だけで主題を伝えようとせず、根拠のない効果や理由も加えない。

例えば、新しいスキルを追加した変更について、次のようにファイル名だけを列挙すると、履歴の読み手には何をするスキルかが分からない。

> SPEC.md、SKILL.md、README.md を追加

セッションで確認した目的が、セッションの意図をコミットメッセージへ反映するスキルの追加なら、次のように表せる。これなら、差分を開く前に追加した機能の主題が伝わる。

> セッションの意図を伝えるコミットメッセージ提案スキルを追加

## 出力と評価

指定がなければ、日本語の一行を一案だけ、言語指定のないコードブロックで提示する。Conventional Commits の type・scope や本文は、求められた場合に付ける。一方、質問が必要な場合は質問を、提案できない場合は理由を示し、暫定案は付けない。

他の文章規則を併用する場合も、指定された専用形式を保つ。

評価では、セッションの意図と現在の変更全体が対応し、その主題を読み取れるかを確認する。また、変更についての事実が保たれ、Git の状態やファイルを変更せずに提案できているかを確かめる。
