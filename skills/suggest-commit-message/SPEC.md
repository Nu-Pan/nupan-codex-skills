# コミットメッセージを提案するスキルの仕様

## 目的と適用場面

セッションで扱った目的と判断を根拠に、未コミット変更全体の主題を伝えるコミットメッセージを提案する。
後から履歴を読む人が、差分を開く前に何の変更かを理解できることを重視する。

利用者が `$suggest-commit-message` を明示した場合だけ適用する。
配布設定では暗黙の適用を無効にする。
裸の呼び出しも提案依頼として扱う。

## 変更の意味を確かめる

利用者の追加指示を優先し、指定がなければ未コミット変更全体を対象にする。
Git リポジトリと staged・unstaged・未追跡を含む non-ignored の変更を確認する。
対象がなければ、提案できない理由を簡潔に示す。
Git の状態とファイルは変更しない。

差分を読む前に、セッションで示された目的や判断、確認済みの作業結果を確認する。意図の根拠はこの文脈に求め、Git 差分は現在の変更との照合に使う。

裸の呼び出しだけで文脈がない場合も、目的を一つの簡潔な質問で確認し、回答を得てから差分を読む。対象と意図の対応を判断できない場合は、その不足を確認する。Git 差分やリポジトリ内の説明から、欠けた人間の意図を補わない。

## 主題を一行で表す

セッションで確認できた目的や結果を、変更全体に通じる言葉で表す。
ファイルや修正項目の列挙で説明を代用しない。
根拠のない効果や理由を加えない。

たとえば、次の列挙では変更の主題が伝わりにくい。

> SPEC.md、SKILL.md、README.md を追加

セッションでその意図を確認できていれば、次のように表せる。

> セッションの意図を伝えるコミットメッセージ提案スキルを追加

## 出力と評価

指定がなければ、日本語の一行を一案だけ、言語指定のないコードブロックで提示する。
Conventional Commits の type・scope や本文は、求められた場合に付ける。
質問が必要な場合は質問を、提案不能なら理由を提示し、暫定案は付けない。

他の文章規則を併用する場合も、指定された専用形式を保つ。

評価では、セッションの意図と現在の変更全体が対応し、その主題を読み取れることを確認する。
変更の事実を損なわず、Git 操作を実行せずに提案できていることを見る。
