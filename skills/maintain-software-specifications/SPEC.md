# maintain-software-specifications の仕様

## 目的

このスキルは、ソフトウェアの正本仕様を作成または変更する作業に適用する。
人間が判断すべき重要事項を明示し、実装者へ委ねられる事項を過剰に規定しない仕様を保つ。

作成または変更後の正本仕様は、次の状態を満たす。

- 実装差を許容しない要求が明示されている。
- 意図的に未定義とする範囲が、実装者が正本仕様と現行成果物から自然に補える規模に収まっている。
- 関連する正本仕様と論理的に整合している。
- 一般的なベストプラクティスより、リポジトリ固有の要求が優先されている。
- 用語と命名が統一され、検索可能である。
- 必要な場合は、goal と non-goal の境界が示されている。
- 利用者が変更を求めていない既存仕様の意味が維持されている。

このファイルは、`maintain-software-specifications` のスキル仕様の正本である。
実行時仕様を変更するときは、先にこのファイルを変更する。

## 適用条件

正本として扱われるソフトウェア仕様の作成または変更に、このスキルを使用する。
対象となる作業には、次の内容を含む。

- 挙動仕様、設計仕様、インターフェース契約、制約の作成
- 既存仕様への要求追加、変更、削除
- goal、non-goal、優先関係、裁量範囲の明確化
- 関連仕様との矛盾を避けるための仕様整理
- 仕様上の用語、表記、命名の統一

正本の置き場所や形式は、対象リポジトリの規約に従う。

## 対象外

次の作業は、このスキルだけの対象にしない。

- 正本仕様ではない一般的な技術文書の執筆
- 仕様を変更しない実装またはテストの変更
- 所見の列挙だけを目的とする仕様レビュー
- 実装だけを根拠に、明示されていない正本仕様を復元する作業
- 正本仕様の網羅性を高めることだけを目的とする分類や説明の追加

仕様レビューには、`review-specification-conformance` を使用する。
実装またはテストの保守には、それぞれ対応するスキルを使用する。

## 用語

### 正本仕様

正本仕様は、対象リポジトリで人間の意図を定義する根拠として指定された文書、schema、設定、宣言、またはテストである。
実装成果物は、正本仕様を具体化する対象であり、それ自体を自動的に正本仕様とはみなさない。

### 未定義部分

未定義部分は、正本仕様が挙動や実装方法を固定していない範囲である。
未定義部分が存在すること自体は問題とみなさない。

## 入力と前提

必要な入力を次に示す。

- 利用者が要求する最終状態
- 対象となる正本仕様
- 対象リポジトリの指示と仕様の優先関係
- 関連する正本仕様
- 実現可能性や既存の不整合を調べる場合に参照する既存実装と既存テスト

優先順位を次に示す。

1. 利用者の明示的な指示に従う。
2. 対象リポジトリが指定する正本仕様と優先関係に従う。
3. 関連する正本仕様を、意味と優先関係の根拠として扱う。
4. 明示されていない内容を、既存実装、既存テスト、一般的なベストプラクティスから新しい正本仕様として補わない。

実装と正本仕様が食い違う場合は、実装を正本として仕様を書き換えない。
実装不可能な要求や制約を発見した場合は、人間が判断するための仕様変更案として分離する。

## 実行時の規則

### 人間が判断すべき事項へ集中する

- 正本仕様の記述、構成、量を、人間が読み直して判断する文脈量が小さくなるように決める。
- 実装差を避けたい重要事項を中心に書く。
- 人間が判断すべき事項と、実装者へ委ねてよい事項の境界を読み取れるようにする。
- 仕様全体を網羅すること自体を目的にしない。
- 将来必要になる可能性だけを根拠に、分類、列挙、説明を追加しない。

### 未定義部分を許容する

- 正本仕様に未定義部分が存在することを許容する。
- 未定義部分は、人間が実装差を許容している範囲として扱う。
- 実装差を許容しない事項は、正本仕様に明示する。
- 実装者が補う範囲を、正本仕様、既存実装、既存テストから自然に導ける小さな範囲に保つ。
- 未定義部分を埋めることだけを目的に、仕様を増やさない。

### 必要な文脈だけを残す

- 必須要件を保ったまま、正本仕様を読むために必要な文脈量を小さくする。
- 同じ内容を複数箇所で述べる場合は、1 箇所にまとめて参照する。
- 同じ意味の記述や冗長な言い回しを重複させない。
- 短縮によって意味、係り受け、責務が曖昧になる場合は、明確さを優先する。
- 簡潔さを理由に、調査根拠、検証結果、重大な留保を省かない。

### 仕様間の整合性と優先関係を保つ

- 正本仕様の間に、解釈の余地がない論理的矛盾を作らない。
- 一方へ従うと別の正本仕様へ必ず違反する状態を作らない。
- 基本原則と具体的な仕様を整合させる。
- 一般的な方針と個別仕様の優先関係を読み取れるようにする。
- 一般的なベストプラクティスと正本仕様が競合する場合は、正本仕様を優先する。

### 実装から仕様を逆算しない

- 正本仕様を調査せず、実装だけから正本仕様を導かない。
- 偶然の挙動、過去の都合、実装上の選択を、そのまま正本仕様へ昇格させない。
- 実装の都合だけを根拠に、正本仕様の変更を提案しない。
- 実装から見える制約は、仕様の実現可能性や矛盾を調べる材料として扱う。
- 実装から見える制約を正本仕様へ反映する場合は、人間の判断を経た明示要求として扱う。

### 用語と命名を統一する

- 同じ概念を同じ名前で表す。
- 複数回登場する概念には、必要に応じて専用の名前を与える。
- typo、誤字、表記揺れを修正する。
- キーワード検索で関連する仕様を見つけられる表記を使う。
- 名前から自然に推測される意味と、正本仕様上の定義を一致させる。
- 実態と異なる推測を強く誘発する名前を使わない。

### goal と non-goal の境界を示す

- 適用範囲の誤読や過剰な実装が起こり得る場合は、goal と対になる non-goal を書く。
- non-goal を書かない場合も、実装しなくてよい範囲を読み違えにくい記述にする。
- goal だけで境界が十分に明確な場合は、non-goal を省略してよい。

### 仕様を変更する

1. 利用者が求める最終状態と変更対象を特定する。
2. 対象リポジトリで正本とされる仕様を特定する。
3. 関連する正本仕様を読み、優先関係と既存の意味を確認する。
4. 固定する必要がある事項と、未定義のまま委ねる事項を分ける。
5. 要求を満たすために必要な最小範囲を変更する。
6. 変更箇所以外の既存仕様の意味を維持する。
7. 関連仕様との矛盾、用語、命名、重複、goal と non-goal を確認する。

## 出力

正本仕様のファイルを変更する依頼では、対象リポジトリの形式に従って変更する。
文章だけを求められた場合は、完成後の仕様を提示する。

未定義部分や人間判断が必要な矛盾を解消できない場合は、次の内容を区別して示す。

- 正本仕様で定義されている事項
- 正本仕様で未定義の事項
- 人間の判断が必要な事項

利用者が求めていない場合は、変更した文書の全文を最終回答へ重複して掲載しない。

## 検証

完了前に、次の条件を確認する。

- 利用者が要求した最終状態が正本仕様へ反映されている。
- 実装差を許容しない事項が明示されている。
- 未定義部分を埋めるためだけの過剰な記述がない。
- 関連する正本仕様との明確な矛盾がない。
- 一般方針と個別仕様の優先関係が読み取れる。
- 実装だけから導いた事項を正本仕様として追加していない。
- 用語、表記、命名が統一されている。
- 必要な goal と non-goal が記載されている。
- 変更対象外の既存仕様の意味が維持されている。

1 つでも満たさない場合は、完了としない。

## 重視する価値

人間が正本仕様を理解し、判断するための認知資源を希少なものとして扱う。
正本仕様の量よりも、重要な人間意図を小さな文脈で正確に伝えることを重視する。

実装には、裁量、過去の都合、偶然の挙動が含まれ得る。
このため、実装をそのまま人間意図の根拠にはしない。
