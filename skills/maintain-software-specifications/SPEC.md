# 正本仕様を保守するスキルの仕様

## 目的と適用場面

利用者が求める最終状態を、関連する既存仕様へ統合する。
人間が大切にする要件と設計意図を、読み直して判断しやすい仕様に保つ。
ソフトウェアの正本仕様を作成・改訂する作業に適用する。
所見の報告だけを行うレビューや、仕様を変更しない実装作業では使用しない。

正本仕様は、対象リポジトリが人間の意図の根拠として指定した文書や契約である。
置き場所と優先関係は、対象リポジトリの規約に従う。

## 要求の根拠を確認する

利用者が要求する最終状態と、調査結果や実装上の事情を区別する。
関連する正本仕様から、必要な要件と設計意図を読み取る。
利用者の明示的な指示を優先し、変更される要求と維持する要求を把握する。

実装とテストは、実現可能性や不整合を調べる材料として使う。
リポジトリが正本として指定していない実装上の選択を、新しい要求へ自動的に昇格させない。
実装上の事情によって重要な要求を変える必要がある場合は、人間が判断できる変更案を示す。

## 原則から必要な区別を示す

何を実現するかと、その判断のよりどころを先に説明する。
実装差を許容しない事項は明示し、実装者へ委ねられる具体化は原則から判断できる形にする。
目的に沿った複数の実現方法があることを、仕様の欠陥とみなさない。
裁量が残るたびに未定義の範囲を列挙する必要はない。

原則だけで必要な判断ができる説明を目指す。
条件、例外、non-goal は、原則からは読み取れない重要な判断を補うために選ぶ。
主文から導ける扱いを言い換えても、読み手の判断材料は増えない。

たとえば「公開済みの資料だけを検索対象にする」で十分なら、「未公開の資料は含めない」という除外説明を重ねない。
必要な終了コードや契約項目のように、個別の値を固定する理由がある列挙は残す。
網羅するためだけの分類や、参考情報から推測した要求は増やさない。

## 関連仕様を一体として組み直す

変更要求の影響を受ける説明を、ファイル境界にかかわらず一緒に読む。
用語の定義、参照先、旧挙動を前提とする説明などをたどり、一貫した改訂に必要な範囲を決める。
その範囲では、要件を素直に表す構成へ置換・統合・削除する。
同じ概念は一つの名前で表し、要求の正本を集約して必要な場所から参照する。

既存文への追記を既定の方法にしない。
例外が重なるときは主文を見直し、今回の変更履歴を知らなくても現在の仕様を理解できる形にする。
差分の小ささより、今後読む人の判断の負担を減らすことを優先する。

推敲では既存要求の意味を保つ。
仕様改訂では、利用者の依頼によって不要になった制約を見直せる。
影響範囲外の既存仕様の意味は維持する。
保証の変更に人間の新しい設計判断が必要なら、その判断点を明らかにする。
通常の構成変更のたびに確認を求めない。

レビュー所見を修正する依頼では、所見を解消するために必要な関連箇所を再構成する。
相反する要求を現行実装に合わせて勝手に選び取らない。

## 完成した仕様を確認する

完成後は、利用者の要求と改訂前の関連仕様に照らして読み直す。
必要な要求の欠落がないことと、根拠のない制約が増えていないことを別々に確認する。
関連する仕様の整合性、用語、参照が保たれ、旧記述と新記述が積層していないことを見る。
別の文章・レビュースキルを、この確認の必須条件にしない。

ファイルの変更では、対象リポジトリの形式で仕様を更新する。
文章だけを求められた場合は完成した仕様を提示する。
結果の報告では、利用者に意味のある仕様変更と、解決に人間判断が必要な事項を簡潔に示す。
